## Storage
- ~~**Large-file ceiling**~~ **— promoted to Phase 7b, 2026-07-27 ([ADR-035](02-decisions.md#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row)).** This item said "if files routinely reach tens of MB, move the blob to **Supabase Storage**… reassess when concrete file-size data exists." The data arrived as a crash: a **43 MB** file took the whole Supabase project down (twice, on two projects — PostgREST OOMs materialising the `jsonb`, `520` on the write and `521` on the read-back, manual restart required), while the anonymous IndexedDB path handles the same file fine. The move is happening now, forced rather than chosen. **Two claims in the old wording were wrong and are corrected in ADR-035:** it is *not* merely a cost lever (it is the only fix that removes a self-inflicted DoS surface), and quota enforcement is *not* unchanged (re-basing the byte quota on `storage.objects` is the bulk of the work).
- ~~**Per-file size limit (likely for v1)**~~ **— also Phase 7b.** GeoJSON Studio is an **editor**; a max-file-size restriction is warranted regardless of backend. It stays a **uniform guardrail, not a plan lever** ([ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)) — one ceiling for everyone, optionally higher for Pro — and it finally has a **server-side home**: the Storage bucket's `file_size_limit`, enforced by the Storage API at the edge. (Under the old design there was nowhere to put it: a DB trigger runs downstream of the crash, and a client cap is bypassable by request replay — ADR-033.) **The number is chosen (2026-07-27): `50000000` — decimal 50 MB, uniform across tiers and environments.** Decimal rather than the binary 52428800 because Supabase's free plan caps uploads at 50 MB (user-confirmed) and a bucket's `file_size_limit` may not exceed the project's global limit; the app's `MAX_FILE_SIZE_FOR_FILE_IMPORT` is aligned down to the same value so client and bucket are one number (**client half done 2026-07-27, Phase 7b-1**; the bucket half lands with `0006`). Two notes: it sits *above* the free tier's 30 MiB total quota by design (the quota stops free users first — so the error they see must be the upgrade prompt, not "file too large"), and it **does not fix the crash on its own** — the 43 MB file passed the pre-existing 50 MiB cap already. A temporary lower cloud-path cap was proposed and **declined**: the user is the sole non-prod user and will avoid large uploads until Storage lands (accepted risk, not mitigated). What remains open is reviewing the *other* ceilings (URL import 3 MiB, geometry-add 1 MiB, conversion 10 MB, export/shapefile 50 MB) as a deliberate set — they bound different things and shouldn't be flattened to one number.
- ~~**Write granularity — whole-document vs deltas**~~ **— RESOLVED 2026-08-01, [ADR-037](02-decisions.md#adr-037--a-file-is-a-snapshot-plus-deltas-whole-document-writes-are-retired); moved into Phase 7b-2.** Parked since v1, made live by the 7b-2 pause, and now decided: **a file is a snapshot plus deltas.** The whole `FeatureCollection` stays one object in Storage (ADR-035's placement), written rarely at checkpoints; edits become **feature-level rows** in a bounded, self-deduplicating change buffer (`public.file_edits`), written on every edit. The cost of an edit no longer depends on the size of the file. **Both the "one blob" and "one row per feature" options below were rejected as stated** — the first because whole-document writes were the actual complaint, the second (`file_features`) because it is a data-model rewrite that pays off only for the many-small-features file shape and **fixes writes by creating a read problem** (200,000 rows through PostgREST on open is the same materialisation that crashed the project). The change buffer takes per-feature *writes* while leaving reads as one object fetch. Two facts made it affordable and are worth remembering: `undo-redo-service.js` **already** records every edit as create/delete/update with the affected features, and feature ids are **already** stable and persisted, so no data migration was needed. The original wording is kept below for the reasoning it captures.
  > **Original entry (superseded):** v1 sends the **entire FeatureCollection** on save (simplest; client-direct + RLS intact). **Still deferred, and ADR-035 does not change it** — object storage keeps whole-document writes, it just makes each one dramatically cheaper (a PUT replaces the object: no TOAST rewrite, no WAL amplification, no dead tuples, no vacuum debt). Real delta benefit still requires a different data model: **one row per feature** (`file_features`), where add/delete/modify become INSERT/UPDATE/DELETE. If ever needed, prefer **client-direct RPC / per-row `supabase-js`** over dedicated Node endpoints (ADR-002 — endpoints reintroduce a hop + re-implement RLS). The two divergent large-file strategies stay distinct: **blob externalisation** (chosen in ADR-035, now under review) vs **per-feature rows** (enables deltas; parked). What ADR-035 *does* make urgent is the cheap half of this problem — see the next item. **Update 2026-07-31 — this item is no longer merely parked; it is the live question.** The user paused 7b-2 partly because "writing the entire file — up to 50 MB — for every burst of edits isn't optimal for a paid product," which is exactly this item, and which ADR-035 explicitly does not fix. **The point to hold on to: this is a data-model problem, not a vendor problem.** Firestore's ~1 MiB per-document ceiling means a 50 MB `FeatureCollection` cannot be a document at all — it goes to object storage (structurally what ADR-035 designed) or gets split per feature, which is `file_features` under another name. Any provider comparison that doesn't decide write granularity first will land back here.
  >
  > *(That last line proved exactly right: the 2026-08-01 review decided write granularity first, and the provider question dissolved without a vendor change. The document-database option raised during it — store each file as a document and patch it in place — was the most serious alternative and is rejected in [ADR-037](02-decisions.md#adr-037--a-file-is-a-snapshot-plus-deltas-whole-document-writes-are-retired) on hard document-size ceilings (DynamoDB 400 KB · Firestore 1 MiB · CosmosDB 2 MB · MongoDB 16 MB, against a 50 MB requirement) and on array addressing, which forces features into a map keyed by id — at which point the document design **is** `file_features` with the pieces in a different container.)*
- ~~**Debounced / coalesced autosave — no longer optional**~~ **— built 2026-07-27 (Phase 7b-1).** Eleven call sites in `draw-manager.js` each fired a full whole-document write; they now coalesce on both storage paths — but on **different windows**, which is the part this item got wrong. Strictly separate from the delta question above, and it does not change it. It was **not** as cheap as this item assumed, in two ways. **First**, coalescing means an edit can be *owed*, which retires ADR-018's free "autosaves are per-op and by-id, so nothing needs flushing" and forces six explicit flush boundaries (file switch, delete, File→New, import, sign-out) — plus a `waitForSaveIdle` helper across 16 e2e reloads, since the suite proves persistence by reloading straight after an edit. **Second (2026-07-28)**, a uniform 1.2 s window *lost user edits* — five points drawn quickly then refreshed persisted three — because the `pagehide` flush meant to cover it does not survive teardown at all. The window is now priced by **how long the last save took**, not by path: cheap (≤500 ms) → **200 ms + a leading-edge write**, costly → **1.2 s**. Path was the wrong axis — the upload-bandwidth argument that justifies the debounce scales with the *document*, not the backend, so coalescing a five-point cloud file protected bandwidth nobody was using. **ADR-025's `beforeunload` guard was pulled forward from 7c** to cover the costly case: it warns, and — the part that actually saves the file — its synchronous dialog buys the in-flight write the time the user spends reading it.
  > **The adaptive window was deleted in 7b-2 ([ADR-037](02-decisions.md#adr-037--a-file-is-a-snapshot-plus-deltas-whole-document-writes-are-retired); done 2026-08-01).** It exists to manage a trade between lost edits and saved bandwidth; deltas remove the trade, so `lastSaveDurationMs`, `lastSaveIsCheap()` and the cheap/costly split all go. A short window may remain as a plain rate-limit on delta writes, priced by nothing and risking nothing. **Note this item's claim that it is "strictly separate from the delta question above, and it does not change it" was right about the *direction* and wrong about the *magnitude*** — deltas do not change what coalescing is, but they change what it is *worth*, from load-bearing data protection to a minor efficiency. **The two lessons stand regardless:** price a window by what a save costs rather than by which path it takes, and never treat a page-hide flush as the reason a window is safe to widen.
- **Storage-object orphan reconciliation (new 2026-07-27, ADR-035).** Postgres `on delete cascade` cannot reach Storage, so deleted accounts and failed writes can leave objects behind. Phase 7b adds a prefix sweep to the existing `POST /api/v1/account/delete` (already `service_role`) and defines the delete ordering; a **periodic reconciliation** of objects with no owning `user_files` row is the backstop and is parked here. Note the account-deletion half is a **compliance obligation**, not housekeeping — that part ships in 7b, not from this list.

## Resilience
- ~~**Occasional "invalid feature" error on refresh after rapid point creation**~~ **— promoted to slice 7b-3 (harden), 2026-08-02.** It is a correctness symptom on the new write path rather than a rough edge, so it is fixed before 7b-4 deletes the fallback, not carried as backlog. Original note follows. Seen in the 2026-08-02 smoke tests. Rapidly creating points, then refreshing, sometimes fails validation on the reconstructed document. **First place to look:** a delta written for a feature gl-draw had not finished assigning an id to — `deltaFeatureId()` returns null for such a feature and `reconcileDeltas` skips it, but a *partially* built feature that already has an id would be recorded as-is and replayed verbatim. Confirm what the offending feature actually looks like in `file_edits` before assuming anything harder; the buffer makes this easy to inspect, which is a rare luxury for a race.
- ~~**Crash-recovery journal (Level 2)**~~ **— promoted to slice 7c, 2026-07-28 ([ADR-036](02-decisions.md#adr-036--local-storage-buffers-cloud-writes-the-recovery-journal-is-promoted-indexeddb-as-a-staging-area-is-rejected)); re-scoped 2026-08-01 to an *outbox for undelivered deltas* ([ADR-037](02-decisions.md#adr-037--a-file-is-a-snapshot-plus-deltas-whole-document-writes-are-retired)).** Its durability justification is **gone** — deltas make an edit durable *in the cloud* about a second after it happens, so the coupling this item existed to break no longer exists. What remains is **offline / connection loss**, which is real and still unbuilt. The buffer now holds **deltas, not whole documents** (so the write can genuinely be immediate), the **recovery prompt largely disappears** (draining an outbox is a retry, not a merge — a prompt survives only for the divergence case), and it shares the local delta store the anonymous path needs anyway. Original wording below. Persist the pending unsaved cloud state to a small IndexedDB buffer keyed by file id, cleared on each successful save and on sign-out; on the next load, offer "Recover unsaved changes?" Still a **deliberate, scoped exception to ADR-004** (one-way, self-clearing, user-confirmed — *not* a sync path). **The "build only if users actually report lost work" trigger is retired:** 7b-1's autosave tuning showed the real problem is that durability was coupled to upload frequency, so the debounce window traded lost edits against saved bandwidth with a single number. A local buffer decouples them, which is worth doing before beta rather than after the first report. Two design constraints discovered there: the journal write must be **immediate** (a debounced journal inherits the teardown failure it exists to solve) and **keyed by file id** (or a journal for file A restores into file B). Sequenced **after 7b-2** because its retry logic must classify failures of the *final* storage backend. ADR-036 also records the larger alternative that was **rejected** — IndexedDB as the source of truth with a sync scheduler.

## Multi-session / concurrent editing
- **Server-side lease for cross-device exclusivity — deferred 2026-08-01 ([ADR-037 addendum](02-decisions.md#adr-037--a-file-is-a-snapshot-plus-deltas-whole-document-writes-are-retired)).** v1's position is that **editing one file from multiple tabs or devices is not supported**, stated in the UI. It is implemented *without* enforcing it perfectly: a **Web Lock** blocks a second tab in the same browser (free — the browser auto-releases on close/crash, so no lease, heartbeat or TTL), and cross-device is **warned but not blocked**, with nothing destroyed because a checkpoint only deletes deltas it actually incorporated. **Why the lease was not built:** any lease needs an expiry, and any expiry opens a window where a lapsed session returns and writes — which is exactly the **offline-outbox** flow the design already supports, so lease and outbox interact badly by construction. A lease would therefore *not* remove the divergence guard either; take-over recreates the same divergence. **Build only if beta shows anyone actually hits it.** Shape if so: a lease column + heartbeat on `user_files`, take-over UX, and a demotion path for the losing session (including what happens to its in-memory document and its outbox — the genuinely nasty part).
- **True concurrent editing** — remains out of scope and is a different product ([ADR-004](02-decisions.md#adr-004--two-isolated-storage-paths-no-sync), [ADR-034](02-decisions.md#adr-034--premium-features-gate-scale-automation-and-distribution-not-capability)). Note the delta model has *improved the floor* without being asked to: two sessions now collide only on features both touched, rather than one whole document overwriting the other. That is a better failure mode, not a feature.

## Compliance / ops
- **Privacy policy + terms of service** — the *pages + signup acceptance* are **Phase 5** ([ADR-027](02-decisions.md#adr-027--phase-5-account-area--compliance): static `privacy.html`/`terms.html` + a required signup checkbox, recorded in `user_profiles` on first login). The legal **content** is the user's to finalise — the drafted pages are a starting point. The ToS must include an **acceptable-use clause** prohibiting general-purpose JSON storage (misuse → suspension) — the intent control for the client-direct non-GeoJSON-write concern ([ADR-033](02-decisions.md#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)).
- **Content validation of stored GeoJSON — decided against ([ADR-033](02-decisions.md#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)).** A user can replay their own client-direct write and store valid-but-non-GeoJSON JSON in their **own** row (self-only, quota-bounded). Guarded by **quota** (cost) + **ToS acceptable-use** (intent) + **reader robustness** (integrity), *not* server/DB content validation — which is bypassable by wrapping arbitrary data in a `FeatureCollection`'s `properties`. **Revisit if file sharing / public links / server-side rendering is added:** the control then becomes *safe rendering / output sanitisation* (not validation), since valid GeoJSON can still carry hostile `properties` strings.
- **Terms re-acceptance on version bump** — v1 records `terms_version` at first login only; it does **not** re-prompt when the current version changes. Add a re-acceptance gate if terms are revised after launch.
- **Reconcile `about.html` privacy section at go-public** — `public/about.html` §04 ("Privacy & data") states "no server/cloud storage", true only for the anonymous free tier. Update it (or split free-vs-cloud) at the Phase 9 go-live, when cloud stops being dark.
- **Account deletion + data export** — deletion is **done** (Phase 4: Node `service_role` → cascade via the `on delete cascade` FKs); **data export** is **Phase 5** (client-direct bundle — ADR-027). Export **as a zip of individual `.geojson` files** (v1 exports one JSON bundle) is deferred.
- **`user_profiles` future fields** — the generic per-user table lands in Phase 5 with only terms columns; display name and other non-preference account fields can be added later without restructuring.
- **Backup tier** — confirm Supabase backup/retention settings when provisioning the **production** project (the Phase 8 beta gate — ADR-014/ADR-030).
- **`service_role` needs explicit table grants (learned 2026-07-23)** — on this Supabase project `service_role` did **not** inherit the default `public`-schema grants, and `BYPASSRLS` does **not** cover table-level privileges, so any **PostgREST** (`.from(table)`) call by the Node service_role client 400s with `42501 permission denied` until the table is explicitly `grant`ed. `0005` now grants `service_role` on `plans` + `user_plans` (the only Phase 6 server-written tables). The Phase 1–5 tables (`user_files`, `user_settings`, `user_profiles`) have the **same latent gap** but are never touched by service_role over PostgREST today (account deletion uses the GoTrue **Admin API**, which needs no table grant; everything else is client-direct). Add the equivalent grants **only if** a future feature gives the Node server a direct table read/write on them. When the **production** project is provisioned (Phase 8), re-verify service_role grants there too — the migrations carry the `plans`/`user_plans` grants, but this is a project-level quirk worth re-checking.

## Phase 3 follow-ups (deferred UI/UX & cleanup)

> Parked during the Phase 3 design ([ADR-018](02-decisions.md#adr-018--phase-3-multi-file-model-and-file-lifecycle)). None block the multi-file round-trip; pick up after 3a–3c land.

- **Import as a new named file** — import currently replaces the *active* file's content; instead create a *new* file named from the source filename (`roads.geojson` → "roads"), with an optional name-override field in the import dialog.
- **File Info metadata** — show name, created date, and last-edited date alongside the existing feature/size/bounds stats.
- **Export default filename** — default the export filename to `<file name>.geojson` rather than the generic name.
- **Last-opened-file pointer** — persist the active file so a cold browser refresh reopens the exact file being viewed (v1 reopens the most-recently-updated row).
- **My Files at scale** — search/filter + pagination for users with many files (v1 is a simple most-recent-first list).
- **Migration dismissed-flag** — let a user permanently dismiss the first-login "save local work" prompt (v1 re-offers while cloud files == 0).
- **Open-on-read-only option** — open a file read-only rather than writable (v1 opens writable, like New/Import).
