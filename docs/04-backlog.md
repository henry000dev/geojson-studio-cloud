## Payments (mechanics settled in ADR-007/020/022; sequencing in ADR-030 — built in Phase 6 test mode, live at Phase 9; the *commercial* shape is the user's)
- **Plan model and pricing** — the concrete **tiers, prices, and per-plan storage limits**. Settled: **free = local, paid = cloud** (ADR-019); pricing is **storage-based** (ADR-022). The actual numbers are the user's to design — **provisional in the Phase 6 build; finalised at Phase 9 go-live using beta usage data** (ADR-030). **Tier *structure* + levers now settled ([ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features), 2026-07-25):** four user-facing tiers (Guest / Free / Basic / Pro), differentiated by **storage capacity + file-count only** — core editing/conversion is deliberately never gated (it's the acquisition funnel); `early_access` renamed **`free`**. **Seeded 2026-07-26 (Phase 7a), still provisional:** `free` 30 MiB / 3 files · `basic` 500 MiB / 50 files · `pro` 20 GiB / 1000 files — monotonic on both axes, with the prices (**$5 / $20**) still display copy only. What remains open is the *numbers*, to be set at go-live from beta usage data.
- **Entitlement enforcement is decided and now built** (ADR-022; ADR-031; `0005_plans_and_quota.sql`, 2026-07-22): a **Postgres trigger** (`enforce_storage_quota`) on `user_files` enforces the per-plan storage quota; `public.user_plans` holds plan state (owner-read-only; written only by the `auth.users` default-plan trigger + the Node webhook), and the `plans` lookup table was **adopted** (limits are data). TBD is the limit *values* (provisional until beta data) and any non-storage entitlements (e.g. premium tools).
- **Lifecycle edge cases** — failed payments, cancellation (what happens to a paid user's cloud files), and **downgrade-over-limit** (decided rule: block growth, allow shrink — implementation TBD).
- **Checkout-return "activating" message (agreed 2026-07-23; do in Phase 7c — was 7b, renumbered 2026-07-27)** — the plan is granted by the **webhook**, which can lag the browser's return from Stripe Checkout by a second or two, so `/account` may briefly still show the old plan. Add a small "your subscription is activating…" notice when returning with `?billing=success` (and optionally a short refetch/poll of `getPlan()`), instead of the current silent stale display.
- **Stripe Managed Payments / merchant-of-record decision (surfaced 2026-07-23; decide at Phase 8/9)** — new Stripe accounts have **Managed Payments** (Stripe as merchant of record + automatic tax) ON by default, which **requires a `tax_code` on every product** or Checkout 400s. Phase 6 opts out **per request** (`managed_payments.enabled = false` in `createCheckoutSession`) so we run classic Checkout and defer the choice. At the commercial gate, decide: **adopt** Managed Payments (set product tax codes + tax registrations; remove the opt-out — Stripe then handles VAT/sales-tax compliance) **or** keep classic Checkout and handle tax ourselves. Recorded in ADR-031.
- ~~**File-count lever — chosen but not built**~~ **— built 2026-07-26 (Phase 7a)** ([ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)). `plans.max_files` + the `enforce_file_count` BEFORE-INSERT trigger (`GS_FILE_LIMIT_REACHED`) + client UX (File→New blocked at the cap, count-vs-limit on `/files` and `/account`). Both levers are now enforced; only the limit **values** stay provisional.
- **API usage limits stay a uniform compute guard; per-user metering deferred** ([ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)). The IP-keyed rate limiter on `/convert` + `/dataset` already protects compute. A future "Pro gets higher limits" perk is a config bump but needs the routes to know the user's plan → the **"unify the two JWTs"** item (Auth/sessions, below) is its prerequisite. Full per-user daily metering (an `api_usage` counter table) waits until compute-cost data justifies it or a genuinely expensive server op exists.

## Premium features (paid-plan value beyond storage; menu settled in ADR-034)

> The paid-plan value axis is **scale / automation / distribution / collaboration — never core capability** ([ADR-034](02-decisions.md#adr-034--premium-features-gate-scale-automation-and-distribution-not-capability); extends [ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)). Core editing/conversion stays free (the acquisition funnel). Items ship **whole-but-narrow** (each finished), never half-built-wide. Promoted individually as launch signal warrants.

- **Already promoted out of this list:** `save-as` + **share-as-URL / publish read-only** → **Phase 7d** *(quick wins; was 7c — Phase 7 renumbered 2026-07-27)*; publish serves *raw* geojson at an unguessable URL, and publish + the existing **import-from-URL** is the v1 collaboration workaround. **Under [ADR-035](02-decisions.md#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row) the planned Node public-read endpoint is largely obsolete** — Storage serves the bytes; the intended design is one private bucket + an `anon`-read RLS policy keyed on a published flag (caveats: cross-table subquery needs prototyping; CDN caching undermines revocation). **`plans.description` + hidden `discount`/`god_mode` plans** → Phase 7a; **bulk export** (first finished bulk slice) → Phase 9 Premium-v1.
- **Post-launch long tail (Phase 10):**
  - *Bulk operations — the rest:* bulk import, bulk delete, bulk conversion (reusing `/convert` + `/dataset`), bulk feature-level edits — gate the *many-at-once automation*, not the single action.
  - *Version history / restore:* automatic snapshots + restore — the paid "scale" counterpart to the manual `save-as` quick win.
  - *Publish, richer:* a discovery/browsable directory, a **rendered** public viewer (the point at which [ADR-033](02-decisions.md#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)'s output-sanitisation becomes the control), embed/iframe, branding controls.
  - *Developer surface:* a personal API token / hosted read endpoint — needs the "unify the two JWTs" item (Auth / sessions, below) first.
- **Deferred / declined ([ADR-034](02-decisions.md#adr-034--premium-features-gate-scale-automation-and-distribution-not-capability)):**
  - *Collaborative editing* (email-invite ACL; teams / "same-organisation"; real-time) — deferred; real-time collab **declined outright**. Cost is dominated by the invite-by-email + claim-on-signup flow, the owner-only-RLS → `file_shares` ACL rewrite, and the whole-document-write clobber (which pulls in the parked per-feature model — see *Storage → write granularity*). Publish + import is the near-term substitute; if ever built, it's a tested phase of its own, not a ride-along.
  - *Priority support / "early preview" perk* — not built. "Preview" is a soft marketing label only; a solo maintainer offers one honest support inbox (AI-assisted reply drafting), not an SLA.

## Storage
- ~~**Large-file ceiling**~~ **— promoted to Phase 7b, 2026-07-27 ([ADR-035](02-decisions.md#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row)).** This item said "if files routinely reach tens of MB, move the blob to **Supabase Storage**… reassess when concrete file-size data exists." The data arrived as a crash: a **43 MB** file took the whole Supabase project down (twice, on two projects — PostgREST OOMs materialising the `jsonb`, `520` on the write and `521` on the read-back, manual restart required), while the anonymous IndexedDB path handles the same file fine. The move is happening now, forced rather than chosen. **Two claims in the old wording were wrong and are corrected in ADR-035:** it is *not* merely a cost lever (it is the only fix that removes a self-inflicted DoS surface), and quota enforcement is *not* unchanged (re-basing the byte quota on `storage.objects` is the bulk of the work).
- ~~**Per-file size limit (likely for v1)**~~ **— also Phase 7b.** GeoJSON Studio is an **editor**; a max-file-size restriction is warranted regardless of backend. It stays a **uniform guardrail, not a plan lever** ([ADR-032](02-decisions.md#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)) — one ceiling for everyone, optionally higher for Pro — and it finally has a **server-side home**: the Storage bucket's `file_size_limit`, enforced by the Storage API at the edge. (Under the old design there was nowhere to put it: a DB trigger runs downstream of the crash, and a client cap is bypassable by request replay — ADR-033.) **The number is chosen (2026-07-27): `50000000` — decimal 50 MB, uniform across tiers and environments.** Decimal rather than the binary 52428800 because Supabase's free plan caps uploads at 50 MB (user-confirmed) and a bucket's `file_size_limit` may not exceed the project's global limit; the app's `MAX_FILE_SIZE_FOR_FILE_IMPORT` is aligned down to the same value so client and bucket are one number. Two notes: it sits *above* the free tier's 30 MiB total quota by design (the quota stops free users first — so the error they see must be the upgrade prompt, not "file too large"), and it **does not fix the crash on its own** — the 43 MB file passed the pre-existing 50 MiB cap already. A temporary lower cloud-path cap was proposed and **declined**: the user is the sole non-prod user and will avoid large uploads until Storage lands (accepted risk, not mitigated). What remains open is reviewing the *other* ceilings (URL import 3 MiB, geometry-add 1 MiB, conversion 10 MB, export/shapefile 50 MB) as a deliberate set — they bound different things and shouldn't be flattened to one number.
- **Write granularity — whole-document vs deltas** — v1 sends the **entire FeatureCollection** on save (simplest; client-direct + RLS intact). **Still deferred, and ADR-035 does not change it** — object storage keeps whole-document writes, it just makes each one dramatically cheaper (a PUT replaces the object: no TOAST rewrite, no WAL amplification, no dead tuples, no vacuum debt). Real delta benefit still requires a different data model: **one row per feature** (`file_features`), where add/delete/modify become INSERT/UPDATE/DELETE. If ever needed, prefer **client-direct RPC / per-row `supabase-js`** over dedicated Node endpoints (ADR-002 — endpoints reintroduce a hop + re-implement RLS). The two divergent large-file strategies stay distinct: **blob externalisation** (now chosen — ADR-035) vs **per-feature rows** (enables deltas; parked). What ADR-035 *does* make urgent is the cheap half of this problem — see the next item.
- **Debounced / coalesced autosave — no longer optional (surfaced 2026-07-27; do in Phase 7b-1).** There is **no debounce at all** today: eleven call sites in `draw-manager.js` each fire a full whole-document write. This is independent of where the bytes live, and the sharpest argument is not server cost but **the user's own upload bandwidth** — re-uploading 20 MB every few seconds on a phone or a weak connection is a real harm that no "large files may be slow" warning excuses. Cheap to build; strictly separate from the delta question above.
- **Storage-object orphan reconciliation (new 2026-07-27, ADR-035).** Postgres `on delete cascade` cannot reach Storage, so deleted accounts and failed writes can leave objects behind. Phase 7b adds a prefix sweep to the existing `POST /api/v1/account/delete` (already `service_role`) and defines the delete ordering; a **periodic reconciliation** of objects with no owning `user_files` row is the backstop and is parked here. Note the account-deletion half is a **compliance obligation**, not housekeeping — that part ships in 7b, not from this list.

## Resilience
- **Crash-recovery journal (Level 2)** — beyond v1's Level 1 (retry + reconnect flush + save-status + `beforeunload`; ADR-025), persist the pending unsaved cloud state to a small IndexedDB buffer keyed by file id, cleared on each successful save; on the next load, detect an orphaned buffer and offer "Recover unsaved changes?" Covers the "tab closed while offline" case. This is a **deliberate, scoped exception to ADR-004** (one-way, self-clearing recovery journal — *not* a sync path). Build only if users actually report lost work.

## Auth / sessions
- **Configure the extra OAuth providers in Supabase (user task)** — the /login page renders **GitHub / Microsoft (azure) / Facebook** buttons alongside Google (2026-07-06; `constants/auth-constants.js`), but only Google is configured on non-prod. Each needs its OAuth app (GitHub OAuth app, Azure app registration, Facebook app) + the Supabase callback URL + dashboard enablement — on non-prod now, and again on the production project at the beta gate (Phase 8 — ADR-030 renumbering). ## Compliance / ops
- **Privacy policy + terms of service** — the *pages + signup acceptance* are **Phase 5** ([ADR-027](02-decisions.md#adr-027--phase-5-account-area--compliance): static `privacy.html`/`terms.html` + a required signup checkbox, recorded in `user_profiles` on first login). The legal **content** is the user's to finalise — the drafted pages are a starting point. The ToS must include an **acceptable-use clause** prohibiting general-purpose JSON storage (misuse → suspension) — the intent control for the client-direct non-GeoJSON-write concern ([ADR-033](02-decisions.md#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)).
- **Content validation of stored GeoJSON — decided against ([ADR-033](02-decisions.md#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)).** A user can replay their own client-direct write and store valid-but-non-GeoJSON JSON in their **own** row (self-only, quota-bounded). Guarded by **quota** (cost) + **ToS acceptable-use** (intent) + **reader robustness** (integrity), *not* server/DB content validation — which is bypassable by wrapping arbitrary data in a `FeatureCollection`'s `properties`. **Revisit if file sharing / public links / server-side rendering is added:** the control then becomes *safe rendering / output sanitisation* (not validation), since valid GeoJSON can still carry hostile `properties` strings.
- **Terms re-acceptance on version bump** — v1 records `terms_version` at first login only; it does **not** re-prompt when the current version changes. Add a re-acceptance gate if terms are revised after launch.
- **Reconcile `about.html` privacy section at go-public** — `public/about.html` §04 ("Privacy & data") states "no server/cloud storage", true only for the anonymous free tier. Update it (or split free-vs-cloud) at the Phase 9 go-live, when cloud stops being dark.
- **Account deletion + data export** — deletion is **done** (Phase 4: Node `service_role` → cascade via the `on delete cascade` FKs); **data export** is **Phase 5** (client-direct bundle — ADR-027). Export **as a zip of individual `.geojson` files** (v1 exports one JSON bundle) is deferred.
- **`user_profiles` future fields** — the generic per-user table lands in Phase 5 with only terms columns; display name and other non-preference account fields can be added later without restructuring.
- **Backup tier** — confirm Supabase backup/retention settings when provisioning the **production** project (the Phase 8 beta gate — ADR-014/ADR-030).
- **`service_role` needs explicit table grants (learned 2026-07-23)** — on this Supabase project `service_role` did **not** inherit the default `public`-schema grants, and `BYPASSRLS` does **not** cover table-level privileges, so any **PostgREST** (`.from(table)`) call by the Node service_role client 400s with `42501 permission denied` until the table is explicitly `grant`ed. `0005` now grants `service_role` on `plans` + `user_plans` (the only Phase 6 server-written tables). The Phase 1–5 tables (`user_files`, `user_settings`, `user_profiles`) have the **same latent gap** but are never touched by service_role over PostgREST today (account deletion uses the GoTrue **Admin API**, which needs no table grant; everything else is client-direct). Add the equivalent grants **only if** a future feature gives the Node server a direct table read/write on them. When the **production** project is provisioned (Phase 8), re-verify service_role grants there too — the migrations carry the `plans`/`user_plans` grants, but this is a project-level quirk worth re-checking.

## Phase 3 follow-ups (deferred UI/UX & cleanup)

> Parked during the Phase 3 design ([ADR-018](02-decisions.md#adr-018--phase-3-multi-file-model-and-file-lifecycle)). None block the multi-file round-trip; pick up after 3a–3c land.

- **Import as a new named file** — import currently replaces the *active* file's content; instead create a *new* file named from the source filename (`roads.geojson` → "roads"), with an optional name-override field in the import dialog.
- **File Info metadata** — show name, created date, and last-edited date alongside the existing feature/size/bounds stats.
- **Export default filename** — default the export filename to `<file name>.geojson` rather than the generic name.
- **Last-opened-file pointer** — persist the active file so a cold browser refresh reopens the exact file being viewed (v1 reopens the most-recently-updated row).
- **My Files at scale** — search/filter + pagination for users with many files (v1 is a simple most-recent-first list).
- **Migration dismissed-flag** — let a user permanently dismiss the first-login "save local work" prompt (v1 re-offers while cloud files == 0).
- **Open-on-read-only option** — open a file read-only rather than writable (v1 opens writable, like New/Import).
