# 02 — Decisions (ADR log)

> **Stability:** stable, append-only. Each record captures a decision, its rationale, and the alternatives rejected — so settled questions are not re-litigated when the epic is resumed cold. Supersede rather than edit: if a decision changes, add a new ADR that references the old one.

Format per record: **Status · Context · Decision · Rationale · Alternatives rejected · Consequences.**

---

## ADR-001 — Backend is Supabase

- **Status:** Accepted. **The inline-blob half is superseded by [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row) (2026-07-27)** — files did reach tens of MB, and inline `jsonb` crashed the project, so the blob moves to Supabase Storage and the "held in reserve" line below is called in. The choice of **Supabase itself** is unaffected; if anything it is vindicated, since the escape hatch was already inside the same product.
- **Context:** Logged-in users need cloud-stored GeoJSON + settings. GeoJSON files can be several MB. Least-effort and pre-integrated are priorities. The team is one person.
- **Decision:** Use **Supabase** (Postgres + Auth + Storage).
- **Rationale:** Postgres stores the GeoJSON blob **inline** in a `jsonb`/`text` column — one store for blobs, metadata, and settings. "Just Postgres" means low lock-in (exit = `pg_dump`).
- **Alternatives rejected:**
  - **Firebase (Firestore + Cloud Storage):** Firestore's **1 MB document limit** would force a metadata-in-Firestore + blob-in-Storage split, reintroducing the two-store complexity we want to avoid.
  - **Mongo + S3 + Clerk/Auth0 (assemble yourself):** more wiring, more services to run, more lock-in surface. Architecture is identical to a BaaS, so the BaaS wins on effort.
  - **Raw S3:** object storage is not a database; it always pairs with a separate DB. Extra system for no gain at typical GeoJSON sizes.
- **Consequences:** Adopt `supabase-js`, Postgres RLS, and the Supabase Auth model. ~~Supabase Storage held in reserve for large files only.~~ **Reserve called in 2026-07-27 — [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row).** Note the rejection of **raw S3** above still holds and is not contradicted: the objection was to pairing an object store with a *separate* database, which is not what ADR-035 does — Storage is part of the same Supabase project, sharing its auth, RLS model, and dashboard.

## ADR-002 — Client-direct access with RLS, not a Node wrapper

- **Status:** Accepted.
- **Context:** The SPA could talk to Supabase directly, or route everything through the existing Node API for a "unified" surface.
- **Decision:** **Client-direct** via `supabase-js`, authorization enforced by **RLS**. Auth always direct to Supabase Auth. The Node API is not a generic CRUD wrapper.
- **Rationale:** A wrapper means re-implementing, imperatively in Node, the per-user isolation RLS gives declaratively — same security-critical work, more code, more risk, an extra network hop for blobs. The decoupling appeal of a wrapper is obtained more cheaply with a **client-side storage-provider seam**. Proxying auth (token refresh, OAuth) is high-effort and bug-prone for zero benefit.
- **Alternatives rejected:**
  - **Full Node wrapper over Supabase:** rejected for effort/risk as above.
  - **Proxying auth through Node:** rejected outright — never proxy auth.
- **Consequences:** RLS policies are the security boundary and must be reviewed/tested deliberately. A thin Node layer may be added **later, selectively**, only for payment/entitlement logic.

## ADR-003 — Data model is users → files; settings stay user-global

- **Status:** Accepted.
- **Context:** Logged-in users want multiple saved files. The app today has a single active document and single global bookmark/template/settings sets per browser.
- **Decision:** Unit of saved work is a **file** (one row per file). Bookmarks, templates, basemap, panel prefs, and measurement units stay **user-global**.
- **Rationale:** Matches current behaviour (nothing is file-scoped today), and is the least-effort model. One DB record per file either way.
- **Alternatives rejected:**
  - **"Project" model (per-file context bundling bookmarks/view/basemap with the GeoJSON):** more data-model and UX work; deferred. Can be adopted later by extending the file row with context fields — no restructuring required.
- **Consequences:** A "My Files" browser (list/open/rename/delete/create) and an "active file" concept in state (Phase 3).

## ADR-004 — Two isolated storage paths, no sync

- **Status:** Accepted.
- **Context:** We want to keep the anonymous experience and add cloud for logged-in users.
- **Decision:** Anonymous users use local (IndexedDB + `localStorage`) only; logged-in users use Supabase only. The two paths never sync.
- **Rationale:** Removes the single hardest workstream (offline/conflict sync). Isolation means a cloud bug cannot corrupt local data, and the always-present local path is an instant kill-switch / rollback.
- **Alternatives rejected:**
  - **Local-first with sync (IndexedDB as cache, server as source of truth):** large effort (conflict resolution, the app auto-saves and has undo/redo). Explicitly out of scope.
- **Consequences:** On first login, migration is an **opt-in, per-user** "import your current local work" prompt — never a fleet-wide event.

## ADR-005 — Runtime URL-param feature flag, not an env/branch flag

- **Status:** Accepted.
- **Context:** The project deploys **staging → production sequentially** (staging is pre-production). The team is one person — no separate testers.
- **Decision:** Gate the account feature behind a **runtime URL-param flag** (`?ff=cloud` persisted to `localStorage`). It controls **only** whether the login UI is visible.
- **Rationale:** Environment-independent — the dark account code rides to production inert while the normal beta release cadence continues. A build/env flag wouldn't isolate, since whatever lands on staging ships to prod. The flag enables **trunk-based development** instead of a long-lived divergent branch.
- **Alternatives rejected:**
  - **Env/build flag (staging-on, prod-off):** doesn't isolate in a sequential pipeline.
  - **Long-lived feature branch:** reintroduces the big-bang merge the flag is meant to kill.
  - **Hosted flag service (LaunchDarkly/PostHog/Flagsmith):** unnecessary infrastructure at this scale.
- **Consequences:** The flag is a **visibility toggle, not a security boundary** (Auth + RLS are the real gate). Dark code must be truly inert (lazy-init Supabase, code-split the account module). The flag is temporary scaffolding — launch ≈ flip default on and delete the flag. **Mechanism refined by [ADR-015](#adr-015--the-cloud-feature-flag-is-url-presence-based-not-persisted):** the flag is URL-presence-based, *not* persisted to `localStorage`.

## ADR-006 — Single codebase, no separate app

- **Status:** Accepted.
- **Context:** One option for a large feature is to fork a new "v2" app and migrate.
- **Decision:** Ship everything in the existing `geojson-studio-app` / `geojson-studio-api` codebases behind the flag.
- **Rationale:** The editor is identical for anonymous users; a fork would duplicate the whole app to add one gated feature, then end in a big-bang migration. The isolation a fork seems to offer is provided instead by the flag + the always-present local path.
- **Alternatives rejected:** Separate app + later migration — higher effort and risk, opposite of incremental.
- **Consequences:** Account code lives on trunk, shipped dark, grown incrementally alongside ongoing beta work.

## ADR-007 — Payments deferred to last

- **Status:** Accepted. **Sequencing amended by [ADR-030](#adr-030--monetisation-built-before-beta-charging-still-goes-live-last) (2026-07-06):** the payment *build* now precedes beta (Stripe test mode); *charging* real users remains last — the rationale below is intact.
- **Context:** The end state includes paid plans, but charging users while the foundation is unproven is risky.
- **Decision:** Build accounts + cloud storage first; add **Stripe** (hosted Checkout + Customer Portal + webhook → `plan` flag) as the **final phase**, after a free beta.
- **Rationale:** No one ever pays while the foundation is still being proven. Payments are an isolated layer that doesn't block the rest.
- **Alternatives rejected:** Build accounts and billing together up front — more upfront work before any validation.
- **Consequences:** Entitlements/quotas are where the *selective* Node layer (ADR-002) earns its keep. Plan specifics are TBD (see [`04-backlog.md`](04-backlog.md)).

## ADR-008 — The session JWT always stays local

- **Status:** Accepted.
- **Context:** Settings migrate to the cloud for logged-in users.
- **Decision:** The Supabase session token (the credential itself) lives only in `localStorage`/the SDK store and is **never** written to the cloud DB.
- **Rationale:** It is a credential, not user content; storing it server-side is both pointless and a risk.
- **Consequences:** The settings-migration split (architecture §6) explicitly keeps the token, and other device-level flags, local.

## ADR-009 — Repository & docs structure

- **Status:** Accepted.
- **Context:** The epic spans two separate code repos that know nothing about each other, plus a growing set of design docs and (later) Supabase schema.
- **Decision:** A dedicated sibling repo **`geojson-studio-cloud`** holds the docs and shared substrate (later: SQL schema, RLS, migrations, entitlements config). Matches the existing `geojson-studio-resources` sibling-repo pattern.
- **Rationale:** This material belongs to neither app nor api. A dedicated repo (not a folder in `resources`) keeps evolving planning/schema separate from static assets and gives it its own history. Named after the **brand** so the technical and product names are unified.
- **Alternatives rejected:** Folder inside `geojson-studio-resources` (mixes concerns); plain non-git folder (loses history); a single monolithic `cloud-accounts-plan.md` (volatile and stable content churn together).
- **Consequences:** Each code repo carries a one-line pointer back to this repo. Branch strategy is short-lived per-phase branches off `staging` with the **same branch name across both code repos** — not one mega-branch (see [`03-rollout.md`](03-rollout.md)).

## ADR-010 — The settings-KV seam is synchronous

- **Status:** Accepted.
- **Context:** Phase 0 introduces a settings provider in front of `localStorage`. The eventual Supabase-backed implementation (Phase 2) is necessarily async. The instinct is to make the seam async now so both implementations share one shape.
- **Decision:** The settings seam is **synchronous** in Phase 0 — a 1:1 mirror of the `localStorage` API.
- **Rationale:** Settings are consumed synchronously. Pinia stores read `localStorage` inside their synchronous `state()` factories (e.g. `measurements.js`, `session.js`, `undo-new-file-toast.js`), materialising state at store-construction time. Converting the seam to async would force every such store to hydrate from a promise — changing store semantics and initial-render behaviour, and breaking the Phase 0 "behaviour-preserving no-op" that the Playwright suite is meant to prove. The file seam is async only because Dexie already is and every consumer already awaits it; the two seams need not share timing, only their method names.
- **Alternatives rejected:**
  - **Async settings seam now:** rejected — turns a mechanical no-op into a semantics-changing refactor of every settings store, defeating the point of Phase 0.
- **Consequences:** Phase 2 keeps the sync interface by hydrating a user's settings into an in-memory cache once on login (async), after which `getItem` reads the cache and `setItem` writes the cache plus a background flush to Supabase. Settings are small KV pairs, so caching them wholesale on login is cheap. The file seam stays async throughout.

## ADR-011 — The session store stays on raw localStorage, outside the settings seam

- **Status:** Accepted. Refines [ADR-008](#adr-008--the-session-jwt-always-stays-local).
- **Context:** Phase 0 routes settings `localStorage` access through the new settings seam. `stores/session.js` holds the Turnstile session JWT in `localStorage`. The settings seam is exactly the abstraction that gains a remote (Supabase) branch in Phase 2.
- **Decision:** `session.js` is **not** migrated to the settings seam; it continues to call `localStorage` directly.
- **Rationale:** ADR-008 already mandates that the session credential never leaves the device. Keeping it off the seam makes that guarantee **structural** rather than a per-key exception someone must remember when wiring up remote routing — the credential simply never touches the code path that can reach the cloud. It is already cleanly isolated (one store, two constants), so excluding it costs nothing.
- **Alternatives rejected:**
  - **Migrate `session.js` to the seam and pin its keys to local in Phase 2:** rejected — relies on a per-key carve-out in the cloud-routing logic; one mistake leaks a credential. Structural exclusion is safer for zero extra effort.
- **Consequences:** The settings-seam migration covers 11 files / 39 calls, not 12 / 45. When Supabase Auth lands (Phase 1+), its session token likewise stays in the SDK/`localStorage` store, never the settings seam.

## ADR-012 — Use the Supabase publishable key, not the legacy anon key

- **Status:** Accepted.
- **Context:** Phase 1 needs a client-side Supabase API key. Supabase now issues two interchangeable client keys: the original JWT-format **anon** key (now labelled *legacy*) and a newer opaque **publishable** key (`sb_publishable_…`). Both are safe to ship in the browser; both are gated by RLS, not by secrecy.
- **Decision:** Configure the client with the **publishable** key. Env var is named for what it is: **`VITE_SUPABASE_PUBLISHABLE_KEY`** (not the originally-planned `VITE_SUPABASE_ANON_KEY`).
- **Rationale:** Supabase's own dashboard now steers new projects to the publishable key and marks the anon key legacy; the publishable key can be rotated independently of the JWT signing secret. Naming the env var `PUBLISHABLE` keeps the code honest about which key is in use. No functional difference to `supabase-js` — it is passed in the same key argument.
- **Alternatives rejected:**
  - **Legacy anon key:** still works, but on the deprecation path; no reason to adopt the older mechanism for greenfield code.
- **Consequences:** Docs and `.env.template` reference `VITE_SUPABASE_PUBLISHABLE_KEY`. The **secret** keys — `service_role` / secret key, the JWT signing secret, and the Google OAuth client secret — are never shipped or committed (the publishable key is the only Supabase key in the client).

## ADR-013 — The cloud feature flag reads raw localStorage at bootstrap, outside the settings seam

- **Status:** **Superseded by [ADR-015](#adr-015--the-cloud-feature-flag-is-url-presence-based-not-persisted).** The flag is no longer persisted, so it doesn't touch `localStorage` at all — this carve-out is moot. Mirrors [ADR-011](#adr-011--the-session-store-stays-on-raw-localstorage-outside-the-settings-seam).
- **Context:** ADR-005 persists the `?ff=cloud` flag to `localStorage`. The settings seam (Phase 0) is the abstraction that gains a remote (Supabase) branch in Phase 2.
- **Decision:** The feature-flag value is read/written via **raw `localStorage`** at app bootstrap, **not** through the settings seam.
- **Rationale:** The flag decides whether the login UI exists at all, so it must be resolvable **before** any auth state or remote routing exists — it logically precedes login. Routing it through a seam that can later point at the cloud would be circular (you'd need to be logged in to read the flag that lets you log in). It is also inherently **device-level** (which browser shows the cloud UI), like the session token, so structural exclusion keeps it off the cloud path for free. The URL→`localStorage` parse runs before Pinia is created so stores see the resolved value in their synchronous `state()` factories.
- **Alternatives rejected:**
  - **Flag through the settings seam:** rejected — circular (needs auth to resolve the gate to auth) and would sync a device-level visibility toggle to the cloud.
- **Consequences:** `feature-flags` store and the bootstrap parser use `localStorage` directly. Like `session.js`, the flag is a deliberate, documented exception to "settings go through the seam". *(Now moot under ADR-015 — the flag is no longer persisted.)*

## ADR-014 — Separate Supabase projects per environment; non-prod set up first

- **Status:** Accepted.
- **Context:** `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` are inlined at build time, per environment. The app deploys staging → production. A Supabase project bundles its own users, data, Auth URL configuration, OAuth redirect allow-list, and keys.
- **Decision:** Use **separate Supabase projects per environment** (at minimum a dedicated **production** project isolated from non-prod). For now, configure **only the non-prod project**; defer the production project and all CI / Dockerfile env-var wiring until the core cloud functionality is proven.
- **Rationale:** Isolation — non-prod testing (throwaway signups, destructive schema/RLS changes) must never touch production users or data. Auth URL config and the Google OAuth callback are project-level and keyed to each environment's origin, so one shared project would have to allow-list every environment at once. Per-project keys map cleanly onto environment-scoped GitHub Variables/Secrets. Deferring prod keeps focus on functionality while the stack is new to the team.
- **Alternatives rejected:**
  - **One shared Supabase project across environments:** rejected — staging activity pollutes production data/users, and a single project must allow-list every origin.
- **Consequences:** Schema + RLS must be kept in sync across projects via **migrations held in this repo** (ADR-009). Production project creation and pipeline/env wiring are **deferred, tracked tasks** (see [`05-worklog.md`](05-worklog.md)). The current project serves local/non-prod. Each environment threads its URL+key the same way the Mapbox token already is: `--build-arg` → Dockerfile `ARG`/`ENV` → Vite (URL as a GitHub *Variable*, publishable key as a *Secret*, mirroring `VITE_API_HOST` / `VITE_MAPBOX_ACCESS_TOKEN`).
- **When "proven" happens (added 2026-07-02).** "Until core cloud functionality is proven" is pinned to the **beta gate (now Phase 8 — ADR-030)** — the first point real external users arrive, and the user's explicit "I'm happy with non-prod" sign-off. Provisioning was originally bundled into Phase 4; it is now the **first task of the beta phase (Phase 8 after ADR-030)**. Nothing between here and then requires the prod project: the Node server layer + account deletion (`service_role`), the account area, and even **Stripe (test mode)** all build against the non-prod project. Prod + Stripe *live* keys are the launch cutover only.

## ADR-015 — The cloud feature flag is URL-presence-based, not persisted

- **Status:** Accepted. Supersedes the persistence mechanism of [ADR-005](#adr-005--runtime-url-param-feature-flag-not-an-envbranch-flag); obsoletes [ADR-013](#adr-013--the-cloud-feature-flag-reads-raw-localstorage-at-bootstrap-outside-the-settings-seam).
- **Context:** ADR-005 chose a runtime URL-param flag. As first implemented it **persisted** `?ff=cloud` to `localStorage` (`ff_cloud=1`) so it survived reloads, with `?ff=cloud:off` to clear. That added a second piece of hidden state: the app could be in "cloud mode" with no visible URL cue, and escaping it needed a special off-param.
- **Decision:** `cloudEnabled` is derived **solely from the presence of `?ff=cloud` in the current URL** at load. Nothing is written to `localStorage`; the param is **not** stripped; there is no `:off` param (removing the param *is* off). Default (no param) = the app behaves exactly as before.
- **Rationale:** Simpler and more predictable — the URL is the single source of truth, the param stays in the address bar as the cue, and the bare domain is always vanilla, so the dark feature can never "stick" for a casual visitor or leak via a persisted flag. Removing persistence also removes the only reason the flag touched `localStorage`, retiring ADR-013's carve-out.
- **Alternatives rejected:**
  - **Persist to `localStorage` + `?ff=cloud:off` (original):** rejected — extra hidden state and a non-obvious toggle model.
- **Consequences:** Reloads keep `?ff=cloud` because it isn't stripped. The OAuth redirect carries `ff=cloud` back via `redirectTo` so the account UI survives the round-trip. A logged-in Supabase session still persists in the SDK store but is only *surfaced* when the flag is present (visibility-only, consistent with ADR-005). The `feature-flags` store reads the URL; no storage-key constant, no bootstrap parser, no `main.js` pre-Pinia step.

## ADR-016 — Phase 2 schema shape (refines the architecture §5 sketch)

- **Status:** Accepted. Implements [ADR-003](#adr-003--data-model-is-users--files-settings-stay-user-global) and the [`01-architecture.md`](01-architecture.md) §5 data model; first migration is `supabase/migrations/0001_files_and_user_settings.sql`. **Superseded in part by [ADR-023](#adr-023--rename-to-user_files-drop-the-backup_geojson-column):** the table is now `user_files` and the `backup_geojson` column was removed (creation scripts amended pre-production).
- **Context:** Phase 2 needs concrete tables for the active GeoJSON document and the settings KV, plus RLS. The architecture §5 sketch (`files{id,user_id,name,geojson}`, `user_settings{user_id,key,value jsonb}`) is the end-state; the first migration only needs what Phase 2 uses, and the storage seams impose a couple of concrete shapes.
- **Decision:** Ship `public.files` and `public.user_settings` with these refinements to the sketch:
  - **One row per user in `files`** — a unique index on `user_id` (`files_one_per_user_uq`), a temporary Phase-2 invariant matching the single local `geojson_data` record; **Phase 3 drops it** for multi-file.
  - **`name` deferred to Phase 3** — unused without a multi-file UI.
  - **`files.backup_geojson` column** — the file seam writes two keys (`geojson_data` + `backup_geojson_data`); ADR-004 forbids logged-in users from using IndexedDB, so the backup blob must live in the cloud row.
  - **`user_settings.value` is `text`, not `jsonb`** — the settings seam round-trips opaque `localStorage` strings; `text` is a lossless 1:1 mirror with no wrap/unwrap.
  - **`user_id default auth.uid()`** so the client may omit it (the `with check` policy still enforces ownership).
  - **RLS to `authenticated` only, owner-scoped (`auth.uid() = user_id`)**, with explicit per-command policies and `revoke all … from anon`; anonymous visitors never touch these tables.
  - **`updated_at` trigger** (`set_updated_at`) for DB-authoritative timestamps; **`on delete cascade`** to `auth.users` for account deletion.
- **Rationale:** Build only what Phase 2 exercises, keep the migration legible, and let the seam contracts (object blob → `jsonb`; opaque string → `text`; two file-seam keys → two columns) drive the column choices. RLS scoped to `authenticated` keeps the anonymous path structurally unable to reach cloud tables.
- **Alternatives rejected:**
  - **`value jsonb` for settings:** rejected — forces wrap/unwrap of opaque strings (some already JSON-encoded), changing the seam's string-in/string-out contract.
  - **Backup stays local in cloud mode:** rejected — violates ADR-004 (no IndexedDB for logged-in users).
  - **Multi-row `files` + `name` now:** rejected — unused in Phase 2; the temporary unique index keeps the round-trip a trivial upsert and is cleanly dropped in Phase 3.
- **Consequences:** Phase 3 migration drops `files_one_per_user_uq` and adds `name` (+ created/updated already present). The remote file provider upserts on `user_id`; the remote settings provider stores/returns `value` verbatim. RLS is verified by the two-account test before the feature is exposed.

## ADR-017 — All user settings follow the account (no device-level carve-out)

- **Status:** Accepted. Supersedes the device-level/account split in [`01-architecture.md`](01-architecture.md) §6 and the Slice 2b `CLOUD_SETTINGS_KEYS` allowlist.
- **Context:** §6 proposed migrating settings *selectively* — keeping "device-level" prefs (colour mode, dismissed-splash/hint flags, etc.) on `localStorage` even when logged in. It was explicitly a *"sensible default … revisit per key"* (also a backlog item), not a constraint. The only firm rule is [ADR-008](#adr-008--the-session-jwt-always-stays-local): the session **credential** stays local — but it is not a setting and already lives outside the settings seam ([ADR-011](#adr-011--the-session-store-stays-on-raw-localstorage-outside-the-settings-seam)).
- **Decision:** For logged-in users, **all settings-seam keys follow the account** (route to the cloud cache). Drop the per-key allowlist. The settings seam reverts to a single `resolveBackend()` (cloud cache when active, else `localStorage`).
- **Rationale:** Users expect their preferences to follow them across devices; the "device-level" rationale was soft caution, not a technical or security need. Removing the allowlist also removes a hidden source of drift (string literals mirrored from individual stores). The credential exclusion is preserved for free because it never passes through the seam.
- **Alternatives rejected:**
  - **Keep the §6 allowlist:** rejected — the user wants all prefs synced; the split added complexity for no clear benefit.
  - **Carve out specific keys (e.g. dark mode, dismissed flags):** considered; the only material nuances are that dismissed flags won't re-show on a new device (usually desired) and colour mode's "system" option still tracks each device's OS. Neither warrants a carve-out.
- **Consequences:** Every settings key persists per-user in `public.user_settings`. A fresh account starts with empty settings (local ones untouched; opt-in migration is Phase 3). Note: in code there is no separate "narrow-screen warning" key — that dialog reuses the `welcomed` flag — so §6's table slightly overstated the local set.

## ADR-018 — Phase 3 multi-file model and file lifecycle

- **Status:** Accepted. Implements [ADR-003](#adr-003--data-model-is-users--files-settings-stay-user-global) (users → files) and refines the Phase 2 single-row model ([ADR-016](#adr-016--phase-2-schema-shape-refines-the-architecture-5-sketch)); drives `supabase/migrations/0002_multi_file.sql`. **The Phase 3b `MyFilesDialog` browsing surface is superseded by the `/files` route ([ADR-029](#adr-029--cloud-account-surfaces-are-routes-not-dialogs), 2026-07-04); the file lifecycle rules in this ADR are unchanged.**
- **Context:** Phase 3 turns the one cloud row per user into multiple named files with an "active file" concept and a "My Files" browser. The single-file model baked in behaviours that multi-file changes: File→New was *destructive* (it replaced the one document), which is the entire reason `backup_geojson` + the "undo new file" toast exist; the remote provider stored exactly one row, writing via `upsert(onConflict: user_id)` and reading via `maybeSingle()` — both lean on `files_one_per_user_uq`.
- **Decision:**
  - **Lazy, non-destructive File→New (cloud path).** New starts a blank in-memory file with *no* active row; the row is inserted on the **first edit** (first autosave). Each used New becomes its own row; repeated New without editing creates nothing. Nothing is replaced (the previous file is already its own row), so the destructive "this will replace your file" confirm is dropped in cloud mode.
  - **`backup_geojson` is vestigial in the cloud.** With New non-destructive, "revert" is just reopening the previous file from My Files. The cloud path never writes `backup_geojson_data`; `createNewFile`/`undoNewFile`/`discardBackup` + the undo-new-file toast stay **local-path-only** (gated by auth state at the *orchestration* layer — `FileToolbar`/`file-service` — not in the seam). The column stays (nullable, unused), dropped in a later cleanup migration.
  - **Remote provider becomes active-row-by-`id`.** `getItem/setItem/removeItem` target the active file by `id` (not the user's sole row). First write with no active file **inserts** a row — serialised through a single in-flight creation promise so exactly one is born — and adopts its id. `setItem` is an **UPDATE-by-id, not an upsert**, so a write racing a delete or a file-switch can't resurrect a deleted row or land on the wrong file. `clear()` is made **safe** (active-row-only / inert) so it can never mean "delete every file". This rewrite ships **with** `0002` dropping `files_one_per_user_uq` (the old upsert/`maybeSingle()` break the instant a second row exists).
  - **Active file resolution & switching.** Cold load (flag-on, logged-in) opens the **most-recently-updated** row (`order by updated_at desc limit 1`); none → blank editor. Switching is **in-place** (clear draw + reset undo/redo + load the row), with any pending autosave **flushed/cancelled first** so it commits to the correct file. **Deleting the active file resets the editor to blank.**
  - **Open and Import keep the file writable** (consistent with today; not read-only).
  - **First-login migration is opt-in via a zero-files trigger.** On login with **zero cloud files** AND **non-empty local work**, prompt *"Save your current local work as your first file?"*. Yes → copy the local GeoJSON into a new cloud file; No/dismiss → nothing (local untouched, reappears on logout). The condition is self-extinguishing — any created file ends it — so no dismissed-flag for v1.
  - **Names** default to "Untitled", suffixed when taken ("Untitled 2"); names are **not unique** (the row `id` is the key).
  - **Unchanged:** bookmarks/templates stay **user-global** (ADR-003), not per-file; multi-tab/device stays **last-write-wins** (ADR-004 — no sync; multi-file adds no conflict handling).
- **Rationale:** Multi-file is a genuinely different feature, so a single auth-state branch at the New-file *orchestration* is honest and keeps the storage **seam uniform** — the active-document I/O (autosave/load/`map-utils`) never changes, which is what isolation (ADR-004) actually protects. Lazy creation gives "each new file is its own entry" without littering My Files with empty rows. By-id + UPDATE semantics close the switch/delete races that upsert-on-`user_id` would open. The zero-files migration trigger needs no extra state and can't nag a user who has adopted the cloud.
- **Alternatives rejected:**
  - **Eager file creation** (insert an empty row per New): clutters My Files, needs empty-row cleanup.
  - **Reinterpreting the existing seam calls in the provider** so the consumer flow is byte-identical across paths: rejected — "create a new file" is a higher-level intent than get/set/remove and differs fundamentally between a single-doc and a multi-file store (`removeItem("geojson_data")` would blank the current file instead of preserving it).
  - **Full page-reload on file open** (like sign-in/out): simpler isolation, but a reload flash and it needs a persisted active-file pointer; in-place switch is nicer and needs none. (Trade-off accepted: a *cold* refresh reopens the most-recent file, not the exact one being viewed — a last-opened pointer is backlogged.)
  - **Read-only on open:** considered; the user chose writable for simplicity/consistency.
- **Consequences:** `0002_multi_file.sql` drops `files_one_per_user_uq` and adds `name`, shipping with the provider rewrite. New code: `stores/active-file.js` (active id + list + lifecycle, `ensureResolved()` mirroring `auth.ensureInitialised()`) and `MyFilesDialog.vue` (Phase 3b). The backup/undo-new-file path is gated to local mode. RLS is unchanged (owner-scoped, already multi-row safe) and re-verified in the two-account gate. Deferred (see [`04-backlog.md`](04-backlog.md)): import-as-new-named-file, File Info metadata, export filename, dropping `backup_geojson`, a last-opened pointer, My Files search/pagination, a migration dismissed-flag.

## ADR-019 — The Cloud epic is a freemium SaaS: free = local, paid = cloud

- **Status:** Accepted. Reframes the epic's commercial scope; builds on [ADR-004](#adr-004--two-isolated-storage-paths-no-sync) (two paths) and [ADR-007](#adr-007--payments-deferred-to-last) (payments last).
- **Context:** The epic began as "optional accounts + cloud-saved work behind a flag." The goal is now explicit: **monetise** GeoJSON Studio as a small freemium SaaS. This crystallises the commercial model on top of the two-paths architecture already built.
- **Decision:** The product is **freemium**, with a split that maps directly onto the existing isolated paths:
  - **Free tier = the local/anonymous app** — the browser-only experience (IndexedDB + `localStorage`), usable forever with no account. It is a **permanent free tier, not a time-limited trial**.
  - **Paid tier(s) = cloud** — accounts + cloud-saved files across devices, gated by a subscription. Cloud storage itself is the paid value; paid tiers differ by **storage quota** (**pricing is storage-based**, since the dominant cloud cost is Supabase storage).
- **Rationale:** The two-paths design (ADR-004) already *is* the free tier, so "use the free version without signing up" needs no trial logic — it's the anonymous path. Storage-based pricing aligns price with the actual cost driver. Keeps the free experience first-class (an existing non-goal to remove it).
- **Alternatives rejected:**
  - **Time-limited trial of cloud:** rejected — the local app is a genuinely useful permanent free product; time-boxing it adds expiry machinery for no gain.
  - **Feature-gated free *cloud* tier:** possible later; v1 keeps it simple — cloud = paid.
- **Consequences:** Introduces paid plans ([ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)), a landing page that frames free-vs-paid ([ADR-021](#adr-021--app-entry-topology-static-landing-at--app-at-app)), and a self-service account area. The `?ff=cloud` flag becomes pre-launch scaffolding retired at go-public. Concrete tiers/prices are the user's to design (backlog).

## ADR-020 — The server-side layer is the existing Node API (not Edge Functions)

- **Status:** Accepted. Makes [ADR-002](#adr-002--client-direct-access-with-rls-not-a-node-wrapper)'s "thin Node layer, added later, selectively" concrete. **Its first concrete build is [ADR-026](#adr-026--server-side-supabase-integration-jwt-verification-service_role-admin-client-account-deletion) (Phase 4 — JWT verification + `service_role` account deletion).**
- **Context:** Payments (Stripe webhook), account deletion, and privileged Supabase writes need server-side code that can't be client-direct (secrets, `service_role`, signature verification). Two candidate hosts: extend the existing `geojson-studio-api` (Node/Express, already deployed), or adopt Supabase **Edge Functions** (Deno, colocated with Supabase).
- **Decision:** **Extend the existing Node API.** Cloud/payment endpoints are new routes there, organised by concern (payment / conversion / storage / dataset). No Edge Functions.
- **Rationale:** The team already runs, deploys, and knows the Node API — least-effort, least new infrastructure. Neither Stripe (backend-agnostic) nor Supabase (`service_role` usable from any server) constrains this. Avoids introducing a second runtime (Deno) to a team still new to Supabase.
- **Alternatives rejected:**
  - **Supabase Edge Functions:** Supabase-native and fine for webhooks, but a new runtime + deploy path for no benefit the Node API doesn't already provide here. A hybrid (webhook-only edge function) was considered and rejected for the same reason.
- **Consequences:** The Node API's prod env gains new secrets — Supabase **`service_role`** key, Stripe secret key, Stripe **webhook signing secret** (wired like [ADR-014](#adr-014--separate-supabase-projects-per-environment-non-prod-set-up-first)'s frontend build-args). Authenticated cloud endpoints **verify the caller's Supabase JWT** server-side; the Turnstile session JWT and the Supabase user JWT coexist (see the backlog's "unify the JWTs"). The Stripe webhook route must read the **raw body** for signature verification (skip global JSON parsing there). `service_role` stays server-only, never shipped.

## ADR-021 — App entry topology: static landing at `/`, app at `/app`

- **Status:** Accepted. Extends the flag decisions ([ADR-005](#adr-005--runtime-url-param-feature-flag-not-an-envbranch-flag)/[ADR-015](#adr-015--the-cloud-feature-flag-is-url-presence-based-not-persisted)) toward go-public. **Delivered in two stages — see [ADR-024](#adr-024--entry-topology-in-two-stages-client-rendered-preview-then-static-seo-landing); this ADR describes the Stage 2 launch form.**
- **Context:** Today the bare domain *is* the editor SPA. A freemium SaaS needs a marketing front door (features, pricing, a "use the free version" entry, sign-up). The app is a Vue SPA served as **static files by nginx on Cloud Run** (Docker); `vue-router` is already present, and nginx already has SPA fallback.
- **Decision:**
  - **`/` = a landing page**, **`/app` = the editor** (Vite `base: '/app/'`, router base `/app/`).
  - The landing is **hand-written static HTML** (a `landing/` source folder, no framework) — **not** a client-rendered SPA route — so it's crawlable for SEO. It's placed by the **Dockerfile** (COPY `landing/` → nginx root; app build → `/app/`), i.e. automatic in CI; nginx gains an `/app/` location beside the root.
  - The landing's **free-tier entry** routes to the anonymous `/app` (no account); **sign-up/login** routes to the cloud experience.
  - This is the **go-public** step that **retires the `?ff=cloud` flag** (ADR-005 always framed it as temporary scaffolding — launch = default-on / delete).
- **Rationale:** A static landing is far more indexable than the SPA shell (better SEO even for the free tool) and fits the existing nginx-static / Cloud-Run model with **no new runtime** (build-time HTML, not SSR). Hand-written HTML is least-effort for one marketing page and stays featherweight. The free-tier button reusing the anonymous path is the ADR-004 / ADR-019 payoff.
- **Alternatives rejected:**
  - **SSR (render per request):** needs a live render server — overkill for a marketing page.
  - **Landing as an SPA route, or an SSG framework (Astro/vite-ssg):** viable, but a client-rendered route is SEO-weak and a framework is unnecessary weight for one page; revisit if the marketing site grows.
- **Consequences:** The app moves under `/app/` (Vite base + router base + nginx location + Supabase Auth **Site URL / redirect allow-list** updated per environment). Old `/` bookmarks now land on marketing. Mostly config + a static page.

## ADR-022 — Monetisation mechanics: `user_plans`, storage quota via Postgres trigger, Stripe

- **Status:** Accepted. Implements the paid side of [ADR-019](#adr-019--the-cloud-epic-is-a-freemium-saas-free--local-paid--cloud); realises [ADR-007](#adr-007--payments-deferred-to-last) (Stripe; sequencing amended by [ADR-030](#adr-030--monetisation-built-before-beta-charging-still-goes-live-last)) via the Node layer ([ADR-020](#adr-020--the-server-side-layer-is-the-existing-node-api-not-edge-functions)).
- **Context:** Paid cloud needs plan state, quota enforcement, and billing. Pricing is **storage-based**; GeoJSON is stored inline in Postgres (ADR-001/016), so "storage used" is the summed byte-size of a user's files.
- **Decision:**
  - **`public.user_plans`** (plural, matching `user_files` / `user_settings`), one row per user: `user_id` PK → `auth.users`, `plan`, `status` (Stripe sub status), `stripe_customer_id`, `stripe_subscription_id`, `current_period_end`. **Server-authoritative:** RLS lets a user **read** their own row; there is **no client write policy** — only the Node API (`service_role`) writes it. Optional `public.plans` lookup (`plan → limit_bytes`, price).
  - **Quota enforced by a Postgres trigger** on `user_files` (`before insert/update`): sum the user's GeoJSON bytes incl. the pending write, compare to the plan's limit, `raise exception` if over. Since writes are client-direct (RLS), the trigger is the real gate; the client shows a usage bar (UX only). **Downgrade-over-limit is humane** — block growth, allow deletes/shrinking; never delete data.
  - **Stripe:** hosted **Checkout** + **Customer Portal** (the portal covers billing history / invoices / cancellation — no custom billing UI); a **webhook** (Node, raw-body signature verify) is the *only* inbound channel and keeps `user_plans` in sync. **Grant entitlements on the webhook, never on the browser's return** from Checkout.
- **Rationale:** Inline-Postgres storage makes usage a trivial `sum(octet_length(...))` and enforcement plain Postgres (robust; Node isn't needed to *enforce*, only to *set* the plan via the webhook). Server-authoritative plan state is essential — a client must never grant itself a plan. Stripe's hosted surfaces minimise custom billing code.
- **Alternatives rejected:**
  - **Client- or RLS-`with check`-only quota:** rejected — aggregate-across-rows checks belong in a trigger; client checks are UX, not a gate.
  - **Plan columns on `auth.users`:** rejected — Supabase-managed schema; business state lives in your own `public` tables.
  - **Custom billing UI:** rejected — the Stripe Customer Portal covers it.
- **Consequences:** New migration(s) for `user_plans` (+ maybe `plans`) and the quota trigger, shipped with the monetisation phase (**Phase 6** after ADR-030; was Phase 8). The Node API gains checkout / webhook / billing-portal routes (ADR-020). ~~"Storage" today = Postgres DB size (not the separate Supabase Storage product); if files grow large, the backlog's move-to-Storage item is the cost lever — quota enforcement is unchanged.~~ **Corrected 2026-07-27 by [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row):** the move to Supabase Storage happened (forced by a crash, not chosen as a cost lever), and quota enforcement **is not unchanged** — it is the bulk of that work. "Storage used" is now the summed size of a user's **objects** (`storage.objects.metadata->>'size'`), not Postgres DB size, and the byte-quota gate moves off `user_files` accordingly. The **file-count** gate (`enforce_file_count`) is genuinely unchanged — it counts metadata rows, which stay in Postgres. Concrete tiers/prices/limits are the user's to design (backlog).

## ADR-023 — Rename to `user_files`, drop the `backup_geojson` column

- **Status:** Accepted. Supersedes the table name + `backup_geojson` column of [ADR-016](#adr-016--phase-2-schema-shape-refines-the-architecture-5-sketch); completes the "drop backup" direction of [ADR-018](#adr-018--phase-3-multi-file-model-and-file-lifecycle).
- **Context:** ADR-016 shipped the active-document table as `public.files` with a `backup_geojson` column (mirroring the file seam's two keys). Phase 3 (ADR-018) made cloud File→New non-destructive, so `backup_geojson` is never written — it was flagged for a later cleanup migration. Separately, `files` is the odd one out beside `user_settings` and `user_plans`. We are **pre-production** (no prod Supabase project — ADR-014), and the non-prod tables were dropped.
- **Decision:**
  - Rename `public.files` → **`public.user_files`** (consistency with `user_settings` / `user_plans`), including its index (`user_files_one_per_user_uq`), policies (`user_files_*`), and trigger (`user_files_set_updated_at`).
  - **Drop the `backup_geojson` column** — the cloud never uses it (ADR-018).
  - Realise both by **amending the creation scripts** (`0001`/`0002`) in place and dropping/recreating the tables, **not** by adding an ALTER/cleanup migration — valid because we're pre-production (nothing applied is immutable yet).
- **Rationale:** Editing the creation scripts keeps the applied schema clean (no vestigial column ever exists, no rename churn) while we still can. Naming consistency across the three per-user tables. The backup column was already agreed vestigial in the cloud (ADR-018).
- **Alternatives rejected:**
  - **An ALTER `0003` migration (rename + drop column):** the correct approach *once production exists*, but adds cruft when the tables can simply be recreated clean. (Drafted, then discarded in favour of editing the creation scripts.)
  - **Keep `files` / the backup column:** rejected — the inconsistency and the dead column are avoidable now.
- **Consequences:** `0001`/`0002` create `public.user_files` with no backup column; the remote provider (`remote-file-storage.js`) targets `user_files` and maps only `geojson_data → geojson` (the local `backup_geojson_data` key is local-only and never reaches it). The migrations README records the pre-prod in-place-amendment policy: once prod exists, migrations become immutable and changes ship as new numbered files.

## ADR-024 — Entry topology in two stages: client-rendered preview, then static SEO landing

- **Status:** Accepted. Refines [ADR-021](#adr-021--app-entry-topology-static-landing-at--app-at-app) (its launch form) and the flag decisions ([ADR-005](#adr-005--runtime-url-param-feature-flag-not-an-envbranch-flag)/[ADR-015](#adr-015--the-cloud-feature-flag-is-url-presence-based-not-persisted)).
- **Context:** ADR-021 fixes the *launch* topology (static HTML landing at `/`, editor at `/app`). But that topology has to be **built and previewed before launch**, and the `?ff=cloud` flag is a **query-string** signal — it can only change client-side behaviour *after* the page loads. It cannot make nginx serve a different static document, and a crawler hits the bare URL with **no** flag at all. So the landing cannot be *both* flag-gated *and* statically SEO-served at the same time — those are two lifecycle stages, bridged by the flag.
- **Decision:** Deliver the entry topology in two stages:
  - **Stage 1 — dark preview (behind `?ff=cloud`).** Everything stays **one SPA at root** (Vite base `/`, router base `/`). Add a `/` route that branches on the flag — present → a **temporary client-rendered `Landing` component**, absent → today's editor — and an `/app` route → editor. `?ff=cloud` **propagates through navigation** (the same trick the OAuth `redirectTo` already uses). **No infrastructure change:** nginx's existing SPA fallback already resolves `/app` to the shell. This preview landing is client-rendered, so it has **no SEO** — acceptable precisely because the flag is dark and nothing crawls it. Bare `/` here = the editor (today's behaviour, untouched).
  - **Stage 2 — launch (now Phase 9 — ADR-030; was Phase 7).** The physical restructure of ADR-021: **hand-written static HTML** landing served by nginx at `/`, the SPA relocated under `/app` (Vite base `/app/`, router base `/app/`, nginx `/app` location, Supabase redirect allow-list), and the **flag deleted**. SEO turns on **here** — only now is the landing a real static document at the bare URL. Bare `/` now = the landing (per ADR-021), replacing Stage 1's editor-at-root.
- **Rationale:** Lets the whole landing + `/app` topology **ship dark and be previewed** like every other epic slice, without prematurely committing to the nginx/Vite/router restructure or paying for SEO tooling before it matters. Separates "does the topology feel right?" (cheap, client-side) from "is it crawlable?" (a launch concern). Resolves the apparent bare-domain contradiction by assigning each behaviour to its stage: Stage 1 bare = editor, Stage 2 bare = landing.
- **Alternatives rejected:**
  - **nginx branching on the `?ff=cloud` query arg** to serve a different static file: fragile, and useless for SEO (crawlers send no query param) — the flag is a client concern by design (ADR-015).
  - **Building the static landing + `/app` restructure up front (skip Stage 1):** couples an early preview to irreversible base-path/nginx changes and loses the ship-dark property.
- **Consequences:** Stage 1 adds a throwaway `Landing` component + two routes + flag propagation, with **zero infra change**. Stage 2 is the ADR-021 work (static `landing/`, base changes, flag retirement) and is where the launch bare-domain topology takes effect. The temporary `Landing` component is **deleted at Stage 2**.

## ADR-025 — Connection-loss resilience for cloud edits (Level 1: retry + reconnect flush + save status)

- **Status:** Accepted. Applies across the logged-in/cloud path; scopes an explicit non-goal (offline-first) against [ADR-004](#adr-004--two-isolated-storage-paths-no-sync).
- **Context:** `supabase-js` has **no offline persistence, queue, or sync** for database operations (unlike Firestore) — offline, a write simply fails. Logged-in users keep **no IndexedDB copy** (ADR-004), so a dropped connection can lose autosaved edits. But the edited FeatureCollection lives **in memory** (draw-manager / Pinia), so it is only *truly* lost if the tab closes/reloads while still offline. Two failure horizons: (1) **tab open, connection returns**; (2) **tab closed while offline**. This is *connection-loss resilience*, deliberately **not** offline-first.
- **Decision:** v1 handles connection loss at **"Level 1"**:
  - **Retry-with-backoff** on the remote autosave write plus a **flush on reconnect** (via the `online` event / the next successful autosave). The in-memory state is the source of truth; on reconnect the latest state is pushed. Covers horizon 1.
  - A **visible save-status indicator** ("Saving… / All changes saved / Offline — retrying, don't close") surfacing the write state, plus a **`beforeunload` guard** that warns when unsaved changes exist. Turns horizon 2 from *silent* loss into a *warned* choice.
  - Lives in the **autosave-service + a small "save-status" Pinia store** surfaced in the UI. **No new durable storage.**
- **Rationale:** Covers the common case (brief blips with the tab open) cheaply, and makes the dangerous case **legible rather than silent**. Matches the product's nature (a client-side editor, not a collaborative sync tool) and honours ADR-004 (no second copy, no sync).
- **Alternatives rejected:**
  - **Level 2 — a crash-recovery journal** (persist pending state to IndexedDB, offer "recover unsaved changes?" on next load): covers horizon 2 fully, but is a **deliberate, scoped exception to ADR-004** (logged-in users otherwise touch no IndexedDB — it's a one-way, self-clearing recovery journal, *not* a sync path). **Backlogged**; build only if users actually report lost work.
    > **Amended 2026-07-28 by [ADR-036](#adr-036--local-storage-buffers-cloud-writes-the-recovery-journal-is-promoted-indexeddb-as-a-staging-area-is-rejected): Level 2 is promoted to slice 7c and the "only if users report lost work" trigger is retired.** 7b-1's autosave work showed the deficiency is structural rather than a matter of frequency — durability was coupled to upload frequency, so the debounce window traded lost edits against saved bandwidth with one number. ADR-036 also finds that the `beforeunload` guard below **warns without writing**, so Level 1 does not in fact cover horizon 2 as this ADR assumed.
  - **Level 3 — full offline-first** (op-queue + conflict resolution): rejected — contradicts ADR-004 ("no sync") and is out of scope for a single-active-document editor. *(ADR-036 re-examines and re-rejects the adjacent "IndexedDB as staging area" proposal, and records the per-feature row model as its real prerequisite.)*
- **Consequences:** The autosave path gains retry/backoff + reconnect flush + a status store/indicator + a `beforeunload` guard. No schema or storage change. Level 2 (recovery journal) is backlogged with the ADR-004 carve-out noted — **promoted to 7c by ADR-036 (2026-07-28)**. The `beforeunload` guard shipped early, in 7b-1 rather than 7c; retry/backoff and reconnect flush remain unbuilt.

## ADR-026 — Server-side Supabase integration: JWT verification (`getUser`), `service_role` admin client, account deletion

- **Status:** Accepted. Makes [ADR-020](#adr-020--the-server-side-layer-is-the-existing-node-api-not-edge-functions) concrete; the first server-side cloud code. Phase 4. Built and tested against the **non-prod** Supabase project ([ADR-014](#adr-014--separate-supabase-projects-per-environment-non-prod-set-up-first)) — no production project involved. **The Phase-5 assumption below (that the account area's usage/export would be Node endpoints) is superseded in part by [ADR-027](#adr-027--phase-5-account-area--compliance) — those are client-direct; deletion is the only account operation on this server surface pre-Stripe.**
- **Context:** Phase 4 needs the first server-side operation that can't be client-direct: **account deletion**, which requires the Supabase **`service_role`** key (bypasses RLS to delete the `auth.users` row). That in turn needs the API to answer *"which logged-in user is calling?"* — the existing Turnstile "session auth" only proves *a human passed a challenge* (bound to IP+UA), it does **not** identify a user. So two new capabilities: verify the caller's **Supabase** JWT, and hold a privileged admin client. The API is an established Node/Express service (`geojson-studio-api`) built around `createApp(config)` with injected config, middleware factories that take secrets + an `enabled` flag (e.g. `createSessionAuth`), and a layered `routes → controllers → services` structure; every existing endpoint is `POST` (RPC/action style) — there is no resource-REST/DELETE surface.
- **Decision:**
  - **Verify the Supabase JWT by delegating to Supabase** — `supabase.auth.getUser(accessToken)` — rather than verifying the signature locally. Supabase validates the token (signature, expiry, revocation, user still exists) and returns the user. Correctness over micro-optimisation; auto-handles key rotation. The ~1 network hop is a non-issue for a rare, destructive endpoint.
  - **New middleware `createSupabaseAuth`** (mirrors `createSessionAuth`): reads `Authorization: Bearer <supabase access token>`, calls `getUser`, attaches `req.supabaseUser = { id, email }`, else `401`. Reusable by later authenticated endpoints (Phase 5 account area).
  - **Two server-side Supabase clients**, built from config and **injected** (so tests stub them, matching the no-`process.env`-below-`index.js` convention): a non-privileged **verify client** (publishable/anon key) for `getUser`, and a **`service_role` admin client** for the privileged delete. Likely `services/supabaseClients.js` → `createSupabaseClients(config)`.
  - **Endpoint: `POST /api/v1/account/delete`** (not `DELETE`). The whole API is already `POST`/RPC-style with no DELETE anywhere, so an action-verb path is *more* consistent than introducing the first resource-REST verb, and reads as an action namespace as the surface grows (`/account/delete`, later `/account/export`). PUT is a semantic mismatch (idempotent *replace*). New `routes/accountRoute.js` + `controllers/accountController.js` + `services/accountService.js`.
  - **Deletion targets `req.supabaseUser.id` from the verified token only** — **never** a user id from the request body (that would be an IDOR / privilege-escalation hole). The debug-secret bypass the other middleware uses does **not** apply here — an endpoint whose entire job is *"who are you"* cannot skip identity; local testing uses a real non-prod dev-login token.
  - **Deletion is `supabaseAdmin.auth.admin.deleteUser(userId)`** (hard delete), which cascades to `user_files` + `user_settings` via their `on delete cascade` FKs. The handler is **tolerant of a repeat call** (already-deleted user → clean success, not an error).
  - **New config / secrets** (read in `index.js setupEnvironment()`, documented in `.env.template`, injected by Cloud Run in deployed envs, pointed at **non-prod** for Phase 4): `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (**secret, server-only, never shipped**), plus an `ACCOUNT_API_ENABLED` toggle so the surface can ship dark. New dependency: `@supabase/supabase-js` (same SDK as the frontend).
  - **Mounting:** a new `/api/v1/account` route group, gated by `createSupabaseAuth` + its own tight rate limiter (like `/session`), inheriting the existing Cloudflare guard + request logger on `/api`. **No changes to the Turnstile path** — session auth stays scoped to `/api/v1/convert` + `/api/v1/dataset`; `app.js` only gains registration lines.
- **Rationale:** `getUser` is the simplest correct verification while the team is new to Supabase; delegating means no local crypto/JWKS surface to own. Reusing the existing Node API + its config/middleware/test idioms keeps this native (ADR-020). The `POST /account/delete` shape matches the codebase's RPC style. Self-only deletion + no debug bypass closes the obvious authz holes on a destructive endpoint.
- **Alternatives rejected:**
  - **Local JWT verification** (JWKS via `jose`, or the legacy HS256 project secret via the already-present `jsonwebtoken`): avoids the network hop but adds crypto surface and can't catch a revoked/deleted user. Revisit **only** if a later phase adds high-frequency authenticated endpoints where the round-trip matters.
  - **`DELETE /api/v1/account`** (resource-REST): rejected — would be the only non-`POST` action endpoint in an otherwise all-`POST`/RPC API; less consistent and no practical gain (identity comes from the JWT, not a body).
  - **Reusing / unifying with the Turnstile session JWT:** out of scope — the two JWTs stay independent (the backlog "unify the JWTs" item); the account surface uses the Supabase JWT only.
- **Consequences:** The API gains its first authenticated-user surface and its first server-side Supabase code + secret (`service_role`). Phase 4 wires everything to **non-prod**; production wiring is the beta gate (now Phase 8 — ADR-014/ADR-030). The shared in-memory rate-limiter block Map means a block tripped on `/account` also applies to convert/dataset and vice-versa (existing behaviour, noted). `@supabase/supabase-js` is added to the API. Later authenticated endpoints reuse `createSupabaseAuth` where they genuinely need the server — but the Phase 5 account area's usage/export turned out to be **client-direct** (RLS), not Node endpoints ([ADR-027](#adr-027--phase-5-account-area--compliance)), so **deletion** is the only account operation on this surface pre-Stripe; the Stripe webhook (now Phase 6 — ADR-030) reuses the `service_role` client but reads the **raw body** for signature verification (ADR-020).

## ADR-027 — Phase 5 account area + compliance

- **Status:** Accepted. Implements **Phase 5** of [`03-rollout.md`](03-rollout.md); realises the self-service account area + compliance basics of the freemium framing ([ADR-019](#adr-019--the-cloud-epic-is-a-freemium-saas-free--local-paid--cloud)); reuses the Phase 4 server layer ([ADR-026](#adr-026--server-side-supabase-integration-jwt-verification-getuser-service_role-admin-client-account-deletion)). **Supersedes in part** ADR-026's forward-looking assumption that Phase 5 would add usage/export **Node endpoints** — they are **client-direct** instead (only deletion stays server-side).
- **Context:** Phase 5 adds self-service account management — storage **usage**, **data export**, **account deletion** (deletion already built in Phase 4) — and the compliance basics (privacy policy + terms, terms acceptance at signup) needed to hold user data (ADR-019). On resuming, four things were open: (a) deliver usage/export client-direct or via Node; (b) account UI as a dialog or a dedicated route; (c) where compliance text lives; (d) how/where terms acceptance is recorded. Grounded in the real repos: the app has `vue-router` (base = `import.meta.env.BASE_URL`) and a static-page pattern (`public/about.html`, served by nginx's `try_files … /index.html` fallback with no per-page config); the api already exposes the Phase 4 `createSupabaseAuth` + `POST /api/v1/account/delete`.
- **Decision:**
  - **Usage & export are client-direct (RLS); no new Node endpoints.** Both are pure reads of the caller's own rows — no secret — which is the ADR-002 default (Node only for secrets / privileged ops). **Storage usage** = a read-only view `public.user_storage_usage` (`security_invoker = on`, so the caller's RLS on `user_files` applies) aggregating `sum(octet_length(geojson::text))` + `count(*)` for the caller, read via `supabase.from("user_storage_usage")` (files only — settings are negligible; matches [ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)'s "summed byte-size of a user's files"; avoids pulling blobs to the client). **Data export** = the client fetches its own `user_files` + `user_settings` (the selects the app already issues) and packages a single downloadable JSON bundle — no server assembly. **Deletion** reuses the Phase 4 `POST /api/v1/account/delete` (it needs `service_role`, so it is the one account op that stays server-side).
  - **The account area is a dedicated SPA route `/account`, not a dialog.** A lazy-loaded, code-split `AccountView.vue` entered from the `AccountMenu` overlay; a route guard redirects non-flag / logged-out visitors to `/`, and internal navigation **propagates `?ff=cloud`** (the flag is URL-presence-based — [ADR-015](#adr-015--the-cloud-feature-flag-is-url-presence-based-not-persisted)) — the same propagation the landing preview (Stage 1 of [ADR-024](#adr-024--entry-topology-in-two-stages-client-rendered-preview-then-static-seo-landing)) needs, pioneered here. The route rides on `BASE_URL`, so it becomes `/app/account` after the go-live restructure (now Phase 9 — ADR-030) with no rework.
  - **Compliance = hand-written static HTML** — `public/privacy.html` + `public/terms.html`, mirroring `public/about.html` (self-contained, same theming, served by the existing nginx static/SPA-fallback — no infra change, crawlable). The *mechanism* is Phase 5; the legal *content* is the user's — authored now as a starting draft, edited later. Linked from the footer, about, the signup checkbox, and the account page.
  - **Terms acceptance lives in a new generic per-user table `public.user_profiles`** (the user's call — not a narrow `terms_acceptances`, and deliberately **not** `user_settings`, which is only app preferences). One row per user (`user_id` PK → `auth.users`, `on delete cascade`); first columns `terms_accepted_at` + `terms_version` (+ timestamps); owner-scoped RLS (select / insert / update own). It is the home for future per-user identity/account fields (display name, non-device onboarding flags, etc.).
  - **Acceptance is gated by a required signup checkbox and recorded on first login.** A checkbox on the signup tab gates **both** "Create account" and "Continue with Google", linking to the two pages. The DB row is written on the **first authenticated session** — an idempotent write of `terms_accepted_at`/`terms_version` when the profile row is absent — because with "Confirm email" ON `signUp()` returns no session and Google signup redirects away, so there is no authenticated context (no `auth.uid()` for RLS) at the signup instant. The checkbox is the consent gate; the row is the audit record.
- **Rationale:** Client-direct keeps Phase 5 almost entirely in the app repo (two small read-oriented migrations, zero Node changes) and honours ADR-002. A route matches SaaS convention, survives deep-linking, and aligns with the go-live `/app` topology. Static compliance pages fit the existing nginx-static / Cloud-Run model exactly (ADR-021's reasoning) with no new runtime. A generic `user_profiles` avoids a single-purpose table and gives future per-user data a home while keeping `user_settings` purely preferences. Record-on-first-login is the only reliable client-direct write point given confirm-email + OAuth redirect.
- **Alternatives rejected:**
  - **Node endpoints for usage/export** (ADR-026's assumption): rejected — no secret is involved; a network hop + re-implemented RLS for a plain owner read (ADR-002). Only `service_role` deletion needs the server.
  - **Account area as a dialog** (like `LoginDialog` / `MyFilesDialog`): workable, but a route is the SaaS norm, deep-linkable, and lines up with the `/app` restructure.
  - **`terms_acceptances` (single-purpose) or a `user_settings` key:** rejected — too narrow / wrong table (settings = preferences). A generic `user_profiles` is the conventional Supabase per-user extension of `auth.users`.
  - **Writing acceptance at the signup instant:** impossible client-direct under confirm-email / OAuth (no session); persisting the ticked intent across the redirect adds fragile state for marginal fidelity.
- **Consequences:** New migrations `0003_storage_usage_view.sql` (usage view) and `0004_user_profiles.sql` (profile table + RLS), applied to non-prod by the user. App repo: `AccountView.vue` + a `/account` route + guard + flag-preserving nav + an `AccountMenu` entry; a client-direct export packager; a signup checkbox + compliance links; a first-login `recordTermsAcceptance()` hook (flag-on, post-auth, beside `cloud-settings-bootstrap.js`); `public/privacy.html` + `public/terms.html`. **No Node changes.** `about.html`'s "Privacy & data" section still describes the local-only model (true for anonymous users) and is reconciled at go-public (now Phase 9 — ADR-030). Backlogged: terms **re-acceptance** on a `terms_version` bump, and **export-as-zip** of individual `.geojson` files.

## ADR-028 — Deploy the cloud-epic branch to staging (Option 2)

- **Status:** Accepted. A CI/process decision that enables validating + polishing the Cloud epic on a real deployed environment before the production gate (beta — now Phase 8, ADR-030) ([ADR-014](#adr-014--separate-supabase-projects-per-environment-non-prod-set-up-first)). No architecture change.
- **Context:** The Cloud epic has been developed and tested only on the developer's laptop (against the non-prod Supabase project). To validate + polish the new cloud UI on a real domain — real OAuth redirects, real email-confirmation links — before production, the long-lived `cloud-epic` branch needs to deploy to **`staging.geojsonstudio.com`**. The existing CI (both repos) deploys the **`staging` branch → staging** and **`main` → production** via GitHub Actions `on: push`, which runs the workflow **from the branch being pushed** — so the `branches:` trigger is per-branch and propagates through merges. The single staging environment (one Cloud Run service per repo) can only serve one branch at a time.
- **Decision:** **Option 2** — repoint the staging deploy to `cloud-epic` and stop using the `staging` branch as a deploy source for the duration of the epic:
  - `deploy-staging.yml` (app + api) trigger `branches: [staging]` → `[cloud-epic]`. This must be applied on **both** `cloud-epic` (to *enable* cloud-epic → staging) **and** the `staging` branch (to *disable* its deploy — its unchanged copy would otherwise clobber the cloud-epic build, since the workflow runs from the pushed branch). `main` keeps its inert copy (never matches a `main` push).
  - `main` → production is **untouched**. Cloud stays isolated on `cloud-epic` (never merged to `main` until launch); normal/urgent fixes go on short branches off `main` → PR to `main`.
  - The `staging` branch remains a normal integration branch (commit / push / PR to `main`); it simply deploys nowhere.
- **Rationale:** `cloud-epic` is effectively the active development line, so it should own the staging environment. Option 2 avoids the per-branch config-drift trap of Option 1 (keeping the staging branch deploying still requires neutralising its trigger, at which point it's a non-deploying integration branch anyway — Option 1 collapses into Option 2 with more moving parts). Production stays fully insulated (only `main` builds prod).
- **Alternatives rejected:**
  - **Option 1 — repoint to cloud-epic but keep the `staging` branch:** viable, but the staging branch's trigger must still be neutralised (else it clobbers), after which it deploys nowhere regardless — more config to keep in sync for no gain.
  - **Option 3 — a dedicated cloud-epic environment** (new Cloud Run service + subdomain, own workflow): zero disruption to the staging-branch workflow and no config drift, but costs a new service + domain mapping + workflow and does not reuse the requested `staging.geojsonstudio.com`. **Kept in reserve** if a separate normal-staging preview becomes necessary during the epic.
- **Consequences:**
  - Cloud is exercised on staging by wiring the **existing non-prod** Supabase into the staging build — frontend build-args `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY`, backend `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SERVICE_ROLE_KEY` + `ACCOUNT_API_ENABLED=true` — **no new Supabase project** — plus adding the staging origin to the non-prod Supabase Auth **Redirect URLs / Site URL** (OAuth + email confirmation currently target localhost). API CORS on staging already allows `https://staging.geojsonstudio.com`.
  - `?ff=cloud` remains the switch on staging too (dark by default). Staging is publicly reachable (`--allow-unauthenticated`), so real signups there create rows in the **non-prod** Supabase project.
  - The normal → prod path loses a deployed-staging preview during the epic (acceptable — staging is rarely used; Option 3 is the escape hatch if it bites).
  - **Launch cleanup** (when `cloud-epic` → `main`): re-point staging back to a normal `staging` branch (or retire it), retire the `?ff=cloud` flag ([ADR-021](#adr-021--app-entry-topology-static-landing-at--app-at-app)), and reconcile the per-branch trigger configs.

## ADR-029 — Cloud account surfaces are routes, not dialogs

- **Status:** Accepted; **fully realised 2026-07-04** (`/login` and `/files` both built). Extends [ADR-027](#adr-027--phase-5-account-area--compliance) (which chose a route for `/account`); supersedes the Phase 1 **LoginDialog** and the Phase 3b **MyFilesDialog** shape of [ADR-018](#adr-018--phase-3-multi-file-model-and-file-lifecycle) (both now deleted). Part of the UI/UX revamp (rollout near-term step 3).
- **Context:** Phase 1 and Phase 3b shipped login and My Files as `GsDialog`-based dialogs inside the editor — least-effort and consistent with the app's tool dialogs at the time. Reviewing for production quality, the user judged dialogs the wrong shape for account-level surfaces: a sign-in **page** is the SaaS convention (deep-linkable, survives reload, and has room for the full mode set — sign in / create account / forgot password / reset password, the last two previously **missing entirely**), and My Files can grow to many files (a page has room for a table, search, and pagination — all backlogged). Editor **tool** dialogs are unaffected; this is only about account surfaces.
- **Decision:** Every cloud account surface is a dedicated, lazy, code-split, flag-gated SPA route riding `BASE_URL` (so they become `/app/login` etc. after the go-live restructure — now Phase 9, ADR-030):
  - **`/login`** (built) — replaces LoginDialog. Four modes via local state seeded from a `mode` query param: `signin` (default), `signup` (deep-linked by the landing's CTAs), `forgot` (new — `resetPasswordForEmail`), `reset` (new — reached from the recovery email, which signs the user in and returns to `/login?mode=reset`; `updateUser({ password })`). Successful sign-in navigates to `/app?ff=cloud` with a **full page load** (the ADR-004 re-bootstrap, as the dialog's reload did).
  - **`/account`** — already a route (ADR-027); its guard now sends logged-out visitors to **`/login`** instead of the landing.
  - **`/files`** (built) — replaces MyFilesDialog. A library page (table of files: open / rename inline / delete / New File; the open file tagged "Open"). Because the editor is unmounted while the page shows, **open = `adoptActiveFile` + navigate to `/app`** and **New File = `startNewBlank` + navigate** (the editor's startup load reads the adopted row through the storage seam); deleting the open file detaches it, so the editor returns blank. On a cold direct load the view awaits `ensureResolved()` before listing so the "Open" badge is correct.
  - **Guards:** all three require the flag (off → `/`); `/login` bounces signed-in users to `/app` **except** `mode=reset`, which operates on the recovery session.
  - **Auth redirects:** Google OAuth now targets `/app` (was: the current pathname); recovery emails target `/login?mode=reset`. Signup confirmation links keep targeting the current origin/path — landing on `/login` signed-in simply bounces to `/app`.
- **Alternatives rejected:**
  - **Keep the dialogs:** wrong idiom for account-level surfaces — not deep-linkable, cramped for the four-mode auth flow, and a file *library* outgrows a dialog.
  - **Auth modal over the landing** (common on marketing sites): still not deep-linkable and couples the landing to the auth code; a route keeps the landing self-contained for its Stage 2 static port.
- **Consequences:** `LoginDialog.vue` deleted; `AccountMenu` navigates to `/login`; the landing's "Sign in" / "Get early access" CTAs deep-link `/login` / `/login?mode=signup`. The Supabase Auth **Redirect URL allow-list must cover `/app` and `/login`** — staging's `https://staging.geojsonstudio.com/**` already does; the production list is wired at the beta gate (now Phase 8 — ADR-014). The flag-off path is untouched (routes are lazy; guards return before touching auth). `MyFilesDialog.vue` is deleted; ADR-018's in-editor file *lifecycle* rules (lazy insert, in-place switch, non-destructive New) are unchanged — only the browsing surface moved.

## ADR-030 — Monetisation built before beta; charging still goes live last

- **Status:** Accepted (2026-07-06). Amends the *sequencing* of [ADR-007](#adr-007--payments-deferred-to-last) (its rationale is preserved); re-orders the tail of [`03-rollout.md`](03-rollout.md) into Phases 6–9.
- **Context:** The remaining phases were 6 (free beta), 7 (landing & go-public), 8 (Stripe + entitlements) — payments last (ADR-007). Planning the beta made a problem visible: the entitlements layer ([ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)'s `user_plans` + storage-quota trigger) **changes the write path of the core product** — writes can be rejected, downgrades block growth. Building it *after* beta means beta users test a quota-less product and the behaviour-changing retrofit lands on them afterwards (possibly with data already over a limit) — effectively requiring a second testing round, invalidating part of what beta proved. Meanwhile nothing in the Stripe work needs production or live keys: the whole Checkout/webhook/portal flow builds in **Stripe test mode** against non-prod (already noted in the old Phase 8 and [ADR-014](#adr-014--separate-supabase-projects-per-environment-non-prod-set-up-first)), with Stripe **test clocks** simulating renewals, payment failures, and cancellations without waiting a billing cycle.
- **Decision:** Build the full monetisation layer **before** beta so beta exercises a production-like system; **charging real users still comes last**. The new tail:
  - **Phase 6 — Monetise (build, test mode):** `user_plans` + quota trigger, Node Checkout/webhook/portal routes, upgrade CTA + usage bar — all against non-prod, with **provisional** tier limits/prices. Create the Stripe account (no activation yet).
  - **Phase 7 — Final polish & debugging:** the consolidated pre-beta gate — the real-account verification backlog, the loose ends, and full lifecycle exercise on staging.
  - **Phase 8 — Free beta / early access:** unchanged in substance; still the **production-provisioning gate** (ADR-014). Beta users get a free `beta` plan row in `user_plans` — the cohort allowlist and the plan mechanism are the same thing — and quotas are **live**. No real charges; optionally a live-mode **100%-off "founders" coupon** if real users should exercise the real Checkout. Stripe **account activation** (business/KYC/bank — days, country-dependent) runs here so it never blocks the cutover.
  - **Phase 9 — Go-live:** absorbs the old Phase 7 **Stage 2** ([ADR-021](#adr-021--app-entry-topology-static-landing-at--app-at-app)/[ADR-024](#adr-024--entry-topology-in-two-stages-client-rendered-preview-then-static-seo-landing): static SEO landing, `/app` move, flag retirement — Stage 1 was already delivered in the UI/UX revamp) plus the payments cutover: live Stripe keys, **final tiers/prices informed by beta usage data**, and the tax-handling decision (e.g. Stripe Tax) before the first live charge.
- **Rationale:** ADR-007's rationale — *no one pays while the foundation is unproven* — survives intact: beta stays free; only the *build* moves. Testing the production-like system once beats retrofitting quotas onto beta users afterwards. Grandfathering ("convert beta users", an old Phase 8 task) reduces to a plan row that already exists. Test mode + test clocks make the full subscription lifecycle testable pre-beta; the one thing beta cannot test without real charges is the live payment moment — which is Stripe's most battle-tested hosted surface, and coverable by the founders coupon if desired.
- **Alternatives rejected:**
  - **Keep payments last (status quo):** rejected — the post-beta quota retrofit changes behaviour under real users and needs its own testing round.
  - **Charge during beta / paid early access:** rejected — exactly what ADR-007 guards against; adds refund/dispute/tax obligations before the product is proven.
- **Consequences:** Rollout Phases 6–9 renumbered (old 8 → 6; old 6 → 8; old 7 Stage 2 → into 9). ADR-014's "beta gate" is now **Phase 8**. Tier limits/prices stay **provisional** until beta usage data exists — they're table rows/Stripe Prices, not architecture, so late changes are cheap; don't publish pricing on the landing until Phase 9. Stale phase numbers in earlier ADRs and the other docs were annotated in place.

## ADR-031 — Phase 6 schema: `plans` as a lookup table; every user gets a server-written `user_plans` row

- **Status:** Accepted (2026-07-22). Refines [ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe) (which left the `plans` table optional and framed free/local users as having "no row") for its concrete Phase 6 build; implements [`03-rollout.md`](03-rollout.md) Phase 6; first migration is `supabase/migrations/0005_plans_and_quota.sql`.
- **Context:** Phase 6 needs concrete answers to two things ADR-022 left open: (1) where per-tier storage limits live, and (2) what the storage-quota trigger resolves for a signed-in cloud user who isn't (yet) a paying subscriber — which, until Phase 8's beta cohort and Phase 9's launch, is *every* cloud user (the whole early-access population).
- **Decision:**
  - **`public.plans`** is a real lookup table (`plan` → `limit_bytes` + display metadata: `label`, `rank`), not hardcoded limits. Changing a tier is a data UPDATE, no code or migration — the point of ADR-030's "tiers are rows, not architecture."
  - **Every user gets a `public.user_plans` row**, defaulted to a new `early_access` plan (the real, DB-authoritative replacement for the client's `QUOTA_BYTES` placeholder), rather than free users having no row. The row is created **server-side**: a `security definer` trigger on `auth.users` insert (`handle_new_user`/`on_auth_user_created`, the standard Supabase pattern), plus a one-time backfill for pre-existing users in the same migration.
  - **`user_plans` stays server-authoritative in the strict sense** (ADR-022's requirement): RLS grants `authenticated` **select only** on their own row — no insert/update/delete grant or policy at all. The only writers are the `security definer` auth-trigger (default row) and, once Slice 6b lands, the Stripe webhook via the `service_role` client (bypasses RLS). A browser can read its plan but can never write itself one, including the default row — that too is server-issued.
  - The storage-quota trigger (`enforce_storage_quota` on `user_files`) reads the limit via `user_plans ⋈ plans`, with a defensive fallback to the `early_access` limit if a row is somehow missing (belt-and-braces given the trigger above guarantees one).
- **Rationale:** A lookup table keeps the promise made in ADR-030 that tiers are cheap to change pre-launch. Giving every user a row (instead of "no row = free") makes the quota trigger's plan lookup total and branch-free — no special-casing "does this user have a plan?" in SQL — and gives the account page's usage bar one consistent code path (`getPlan()` always returns something) instead of a null-plan UI state. Doing it via an `auth.users` trigger (not a client write) is what keeps `user_plans` genuinely server-authoritative per ADR-022 — a first-login *client* write, even of a harmless default, would mean the row's existence depends on the client behaving, and a compromised or buggy client could in principle write an arbitrary plan the first time. The auth trigger closes that off structurally, the same way ADR-011's structural credential exclusion works.
- **Alternatives rejected:**
  - **No row for free/unsubscribed users; trigger falls back in application logic (`coalesce` to a hardcoded default when the join misses):** works, but means "free" is a special case threaded through the trigger and the client, rather than data. Also reintroduces exactly the "no row = ambiguous state" the account page had with `QUOTA_BYTES`.
  - **Client writes its own default `user_plans` row on first login** (the same shape as the Phase 5 `recordTermsAcceptanceOnFirstLogin()` pattern): rejected — `user_plans` is explicitly the one table ADR-022 says must never be client-writable, even for a "safe" default value; an auth-trigger is no harder to build and closes the gap structurally instead of by convention.
  - **Hardcode limits in the trigger + a client constant:** rejected — two sources of truth for the same number, and every tier change needs a migration + a client edit, contradicting ADR-030's provisional-tiers stance.
- **Consequences:** `0005_plans_and_quota.sql` ships `plans`, `user_plans` (read-only RLS), the `handle_new_user` auth-trigger + backfill, and `enforce_storage_quota`. Slice 6b's Stripe webhook is the only other writer of `user_plans`, using `service_role` (bypasses RLS by design, same posture as Phase 4's account deletion). The client's `getPlan()` (Slice 6c) can assume a row always exists.
- **Addendum (2026-07-23) — two fixes from the first test-mode checkout run:**
  - **`service_role` needs explicit table grants.** `BYPASSRLS` covers RLS *policies*, not table-level `GRANT`s, and on this project `service_role` did not inherit the default `public`-schema grants — so the webhook/checkout's PostgREST calls hit `42501 permission denied for table user_plans`. It went unnoticed because Phase 4 deletion uses the GoTrue **Admin API** (needs no table grant), making Phase 6 the first `service_role` *PostgREST* path. `0005` now grants `service_role` `select` on `plans` and `select,insert,update` on `user_plans`. (Detail + the latent gap on the Phase 1–5 tables: [`04-backlog.md`](04-backlog.md).)
  - **Stripe Managed Payments opt-out.** New Stripe accounts default **Managed Payments** (Stripe as merchant of record + automatic tax) ON, which 400s Checkout unless every product carries a `tax_code`. Phase 6 passes `managed_payments: { enabled: false }` on the Checkout Session to run **classic Checkout** — the least-commitment choice that keeps the build moving without adopting a merchant-of-record/tax model. Whether to *adopt* Managed Payments (product tax codes + tax registrations, and drop the opt-out) is a commercial decision deferred to Phase 8/9 (backlog).
- **Addendum (2026-07-26, Phase 7a) — entitlement must not depend on a Stripe dashboard setting.** The webhook originally reverted the plan only on `customer.subscription.deleted`. But how a *dunning* failure ends is configurable in the Stripe dashboard: "cancel the subscription" produces that delete event, while the equally valid "mark the subscription unpaid" produces a `customer.subscription.updated` carrying a non-granting status and **no delete event ever** — leaving the paid plan in place indefinitely (found in the 2026-07-24 dunning test). The `updated` branch now treats the **terminal** statuses (`unpaid`, `incomplete_expired`, `canceled`) as a revert to `free`, keeping the subscription id since the object still exists in Stripe. `past_due` remains granting by design — that is the grace window, not a terminal state. The general point: an entitlement rule that only holds under one dashboard configuration isn't a rule.

## ADR-032 — Plan tiers differentiated by storage and file-count, not features

- **Status:** Accepted (2026-07-25). Refines [ADR-019](#adr-019--the-cloud-epic-is-a-freemium-saas-free--local-paid--cloud) (which framed the split as "free = local, paid = cloud"), [ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe) (storage-only differentiation), and [ADR-031](#adr-031--phase-6-schema-plans-as-a-lookup-table-every-user-gets-a-server-written-user_plans-row) (the `early_access` plan name). A product-shape decision only — the mechanism (the `plans` lookup, server-authoritative `user_plans`, the quota trigger) is unchanged.
- **Context:** Phase 6 is built; the commercial *shape* now needs settling. ADR-019 framed free as local-only and cloud as paid, but ADR-031 already seeds a free cloud allowance (`early_access`) — so in practice there are **three tiers from the user's point of view**, and the "why upgrade" story rested on storage size alone (the weak-differentiator problem flagged in the pricing backlog). The core tool — editing and format conversion — is also the **acquisition funnel** (users arrive via "convert X to GeoJSON online"), so how much of it to gate is a live risk.
- **Decision:**
  - **Four user-facing tiers** — three are cloud plans in `public.plans`; **Guest** is the anonymous local path (no account, no plan row):

    | | **Guest** (anon, local) | **Free** (cloud) | **Basic** (paid) | **Pro** (paid) |
    |---|---|---|---|---|
    | Sync / persistence | this browser, 1 device | cloud, all devices | cloud, all devices | cloud, all devices |
    | Files | 1 | few (e.g. 3) | more (e.g. ~50) | unlimited |
    | Storage (total) | browser-limited | small (e.g. ~250 MB) | mid (GB) | large (GB) |

    *Numbers are illustrative and provisional until go-live (ADR-030); they must be monotonic (Guest ≤ Free < Basic < Pro) — the current `0005` seed is not (`basic` 250 MB sits below free 1 GB, a placeholder to fix). Guest is inherently one file (the browser-storage mechanism has always held a single document).*
  - **The free tier spans two things:** the anonymous local app **and** a permanent, no-payment **free cloud** plan (the renamed `early_access`). This is the refinement of ADR-019 — signing in for free buys **durability + multi-device + more files**, never "the ability to work," which is identical at every tier.
  - **Differentiate on storage capacity and file-count only. Do NOT gate core functionality** (editing, format import/export/conversion). Core value stays available at every tier — gate *scale and persistence*, not *capability*. Each tier is a strict superset of the one below (Guest's single file makes Free's few-files a clean step up, never a downgrade on sign-up).
  - **Rename `early_access` → `free`** (both the `plan` slug and the `label`). "Freemium" is rejected as a tier name — it names the *business model*, not a plan; "Free" is what users understand. (`beta`, added in Phase 8, is unaffected.)
  - **Per-file size is a product guardrail, not a plan lever.** For the free tiers a per-file cap is redundant with the total-storage quota; its real purpose is protecting editor performance and whole-document write cost. Set one sensible ceiling for everyone after the large-file testing (already a Phase 7 item), optionally higher for Pro. Today's de-facto ceiling is **inconsistent** — the conversion API caps uploads at 10 MB, but a native GeoJSON saved **client-direct** to Supabase bypasses the API and is bounded only by the total quota — which is exactly why a deliberate uniform cap is wanted.
  - **API usage limits stay a uniform compute guard, not a plan lever.** The existing IP-keyed rate limiter on `/convert` + `/dataset` already protects compute; per-user metering is deferred — it would re-gate the funnel, meter a near-zero marginal cost (disk, not conversion compute, is the cost driver), and add a hot-path DB write. Any future "Pro gets higher limits" perk is a config bump on that limiter, but it needs the routes to know the caller's plan — which requires the **two-JWT unification** (backlog) as a prerequisite.
- **Rationale:** Gating scale/persistence rather than core value is the standard freemium pattern for a tool whose single-shot task is its own advertisement; crippling conversion would throttle acquisition to protect a cost (compute) that isn't the real driver (disk — the unit-economics finding). File-count is a legible, already-cloud-enforceable axis that separates casual from serious use, adding a second lever beyond storage without touching capability. A permanent free cloud tier (not a trial) keeps ADR-019's "free is first-class" stance while making the sign-up value — durability, multi-device — explicit.
- **Alternatives rejected:**
  - **Gate formats / import-export by tier** (e.g. "Shapefile export is paid"): rejected — that's the core value and the acquisition funnel; a converter that won't convert for free loses the signup it would have won.
  - **Per-day conversion quota per plan:** rejected for launch — soft-gates the funnel, optimises a near-zero cost, and needs metering infra + the JWT unification.
  - **"Freemium" or "Early access" as the free tier's name:** rejected — "freemium" names the model; "early access" implies a time-boxed beta perk, contradicting a *permanent* free tier. "Free" is accurate and plain.
  - **Time-boxed trial of cloud** (revisited from ADR-019): rejected again — a permanent free tier with no expiry machinery, per the user.
- **Consequences:**
  - **New build work, not yet implemented — the file-count lever.** The `0005` quota trigger enforces **storage only**. File-count needs a `max_files` (or similar) column on `plans`, a `user_files` BEFORE-INSERT count check (block a *new* file over the limit; deletes/updates always allowed, mirroring the humane-downgrade rule), and client UX (count vs limit; block "New file" at the cap with an upgrade CTA). Logged in [`03-rollout.md`](03-rollout.md) Phase 7.
  - **The `early_access` → `free` rename** is a schema + code change: the `0005` seed / `user_plans` default / `handle_new_user` / backfill / quota fallback; the webhook's revert literal in the API's `billingService.js`; any client reference or label; tests. Cheap and clean **now**, pre-production (ADR-023's amend-in-place policy) — the user re-applies `0005`. Sequenced into Phase 7 (or done ad hoc).
  - **Storage seed values** need reordering to be monotonic (free < basic < pro); final numbers still wait for beta data (ADR-030).
  - **`00-overview.md` and ADR-019's "cloud = paid" wording** want a light reconciliation to acknowledge the permanent free-cloud tier (the overview glossary already half-says it).
  - The entitlement **mechanism is untouched** (ADR-022/031): plans stay data rows, `user_plans` stays server-authoritative, the quota trigger stays the gate.
- **Addendum (2026-07-26) — built in Phase 7a; the three implementation choices this ADR left open:**
  - **Provisional limits, chosen by the user and now seeded** (still provisional until go-live — ADR-030): `free` 30 MiB / 3 files · `basic` 500 MiB / 50 files · `pro` 20 GiB / 1000 files. Monotonic on both axes, which is what the reorder was for.
  - **"Unlimited" is a sentinel, not `NULL`.** Pro takes a real, large file cap rather than an unbounded one, and `plans.max_files` is `NOT NULL` — so a row that forgets the column is *rejected* instead of silently reading as no gate. The one plan that is effectively ungated (`god_mode`) says so with sentinel values, matching how `limit_bytes` already worked. The cost is that "unlimited" is a marketing word for "1000", which is the right trade at this scale: a fail-closed schema beats an honest adjective.
  - **File-count is enforced `BEFORE INSERT` only** (`enforce_file_count`, raising `GS_FILE_LIMIT_REACHED`), never on update or delete — the same humane-downgrade rule the storage trigger follows. A downgraded user keeps and can still edit every file they have; only *adding another* is refused. The client blocks File→New at the cap before blanking the editor, but that is UX: the trigger is the gate, and the client check fails open.
- **Addendum (2026-07-27) — the per-file guardrail finally gets a server-side home, and the landing page is currently lying about it.** Two things this ADR left soft turned out to matter:
  - **The guardrail had nowhere to live.** This ADR asked for "one sensible ceiling for everyone" but the architecture had no place to enforce it: a client cap is bypassable by request replay ([ADR-033](#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)), and a DB trigger runs *downstream* of the PostgREST memory blow-up that a large file causes, so it never fires. Under [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row) the ceiling becomes the Storage bucket's `file_size_limit`, rejected by the Storage API at the edge — a real server-side control, set once in the migration.
  - **The ceiling is set: 50 MB, uniform across all tiers** (the user's call, 2026-07-27). Chosen to match the cap the app **already** applies to file import (`MAX_FILE_SIZE_FOR_FILE_IMPORT` in `constants/file-constants.js`), so the cloud ceiling and the editor's existing hard cap become one number rather than two that drift. No per-tier variation, including Pro: this ADR's "optionally higher for Pro" is **declined**, keeping it a pure guardrail with nothing to reason about per plan.
    - **Value: `50000000` (decimal 50 MB), not the binary 52428800.** The user confirmed (2026-07-27) that Supabase's **free plan caps uploads at 50 MB**, with paid plans much higher — so the ceiling sits exactly on the platform boundary and the binary/decimal question stops being pedantry. Supabase also requires a bucket's `file_size_limit` to be **≤ the project's global limit**, so 52428800 risks being rejected or clamped, and would in any case create a ~2.4 MB band where the client accepts a file that Storage then refuses. The decimal value is unambiguously safe under either reading, at a cost of 2.4 MB of headroom. **The app's `MAX_FILE_SIZE_FOR_FILE_IMPORT` is aligned down to the same number** so client and bucket are one value — a marginal tightening of the anonymous path that no user will notice, and worth it to remove the drift this addendum exists to prevent.
    - **Uniform across environments too.** Non-prod is on the free plan; production (Phase 8) will likely allow more. The migration still sets 50 MB everywhere — raising it later is a bucket-config change, not a code change, and there is no reason for the product's ceiling to differ by environment.
    - **Below the free tier's total quota, by design.** Free is 30 MiB total, so a free user can never store a 50 MiB file — the storage quota stops them first. That is this ADR's "for the free tiers a per-file cap is redundant with the total-storage quota," working as intended. The consequence is a **UX requirement**: such a user must get the *quota/upgrade* message, not a "file too large" one — which is exactly the import-path gap where quota rejections currently bypass `PlanLimitDialog` (Phase 7b-1).
    - **It does not, on its own, fix anything.** The 43 MB file that crashed the project **passed the pre-existing cap already**. 50 MB is the correct *destination* ceiling; only the move to Storage makes it a safe one ([ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row)). A temporary lower cloud-path cap was proposed for the interim and **declined by the user** (sole non-prod user; will avoid large uploads until Storage lands) — an accepted risk, recorded rather than mitigated.
  - **`LandingView.vue` advertises a per-file lever that does not exist, at figures that are also wrong.** The pricing table claims "Files up to 10 MB each" (Basic) and "Files up to 50 MB each" (Pro) — directly contradicting *"per-file size is a guardrail, not a plan lever"* — alongside storage figures (250 MB / 5 GB) that predate the seeded 500 MiB / 20 GiB. **Nothing enforces a per-file cap anywhere in the product today.** Fixing the copy is a rollout task; the point of record here is that the landing must describe the two levers this ADR actually chose (total storage + file count) and nothing else. Publishing pricing at all stays a Phase 9 decision (ADR-030).

## ADR-033 — No server-side GeoJSON content validation; integrity via quota and ToS

- **Status:** Accepted (2026-07-25). Builds on [ADR-002](#adr-002--client-direct-access-with-rls-not-a-node-wrapper) (client-direct writes; RLS is the boundary) and the storage quota of [ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)/[ADR-031](#adr-031--phase-6-schema-plans-as-a-lookup-table-every-user-gets-a-server-written-user_plans-row).
- **Context:** Logged-in users' GeoJSON is written **client-direct** to `public.user_files.geojson` (a `jsonb` column), authorised only by owner-scoped RLS — no Node hop on the write path, and the server treats the blob as opaque (server-side GeoJSON processing is a stated non-goal). Client-side GeoJSON handling is therefore a **UX guardrail, not a security boundary**: a user can read their own auto-save request in devtools and replay it (curl/Postman) with any body, using their own valid token. `jsonb` already rejects *malformed* JSON, so the residual is **valid JSON that is not GeoJSON** — raising the concern that `user_files` could become a store for non-GeoJSON data / a general-purpose JSON backend.
- **Decision:** Do **not** add server- or DB-side GeoJSON **content** validation. The write path stays client-direct; integrity and abuse are handled by three content-agnostic or intent-level controls:
  1. **Quota — the real cost/abuse bound.** The `0005` storage-quota trigger, plus the per-file size cap and file-count lever (Phase 7), bound cost and scale **regardless of content** — arbitrary JSON costs the same disk as GeoJSON and is capped identically.
  2. **ToS acceptable-use clause — the intent control.** The terms prohibit using cloud storage as a general-purpose JSON backend; misuse → suspension. Authored with the Phase 7c legal content *(was 7b — Phase 7 renumbered 2026-07-27 when the ADR-035 storage move became the new 7b)*.
  3. **Reader robustness — the integrity control.** The app reads back non-GeoJSON / malformed data **gracefully** (a clear "couldn't load as GeoJSON" state, no crash, a raw-view/export escape hatch), covering corruption from *any* cause — a replayed write, a bug, a partial save, format drift. A Phase 7c task *(was 7b)*.

  Client-side validation is kept as a UX guardrail only.
- **Rationale:**
  - **Self-only blast radius.** Owner-RLS confines a user to their own quota-limited row — no cross-user or system exposure. This is *data integrity*, not a breach.
  - **Validation neither prevents abuse nor makes content safe.** Any structural GeoJSON check is bypassable by wrapping arbitrary data in a valid `FeatureCollection` (`geometry: null`, payload under `properties`), so it deters only *casual/accidental* non-GeoJSON, not the motivated actor in the threat scenario (who is, by definition, replaying a request). The correct cost bound is the content-agnostic quota; the correct intent control is ToS.
  - **Preserves [ADR-002](#adr-002--client-direct-access-with-rls-not-a-node-wrapper).** A validating Node write-proxy would reintroduce a server hop on the core write path and re-implement ownership — for no security gain the wrapper doesn't defeat.
- **Alternatives rejected:**
  - **Shallow DB `CHECK`/trigger on the GeoJSON top-level shape** (is an object; `type` ∈ the GeoJSON types; `features` is an array for a FeatureCollection): considered, declined. Bypassable by wrapping, adds hot-path cost on every save, and its only real value is a uniform "always GeoJSON-shaped" invariant we don't need. Remains available later — amend-in-place `0005` pre-prod, or a new migration post-prod — if such an invariant is ever wanted.
  - **Deep validation** (a Node GeoJSON library, or PostGIS `ST_GeomFromGeoJSON`): full validation on every save; rejected as heavy for a self-only integrity concern and, again, defeated by property-wrapping for the abuse case.
  - **Do nothing, undocumented:** rejected — the stance deserves recording so "shouldn't we validate GeoJSON server-side?" is not re-litigated cold.
- **Consequences:**
  - The ToS acceptable-use clause and the graceful-read-back task are logged in [`03-rollout.md`](03-rollout.md) Phase 7c *(was 7b)*.
  - **Revisit trigger — sharing.** If **file sharing / public links / server-side rendering (thumbnails, exports)** is ever added, a file is consumed by a party *other than the owner*, and the real control becomes **safe rendering / output sanitisation** — still **not** GeoJSON validation, since valid GeoJSON can carry hostile `properties` strings. Design that into the sharing feature; audit any `v-html` / Mapbox popup `innerHTML` in the app repo at that point (Vue escapes `{{ }}` by default).
- **Addendum (2026-07-27) — the residual widens under [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row); the decision itself is unchanged.** With the blob moving from a `jsonb` column to a Storage object, the framing above ("`jsonb` already rejects *malformed* JSON, so the residual is valid JSON that is not GeoJSON") no longer holds: an object store accepts **arbitrary bytes**, not even necessarily JSON. Effects on the three controls:
  - **Quota (cost)** — unaffected. It was always content-agnostic; bytes are bytes. It also gains a genuine per-file ceiling for the first time (the bucket's `file_size_limit`).
  - **ToS acceptable-use (intent)** — unaffected, and if anything more clearly the right control: the clause prohibits using cloud storage as a general-purpose backend regardless of what format the misuse takes.
  - **Reader robustness (integrity)** — **promoted from prudent to required.** It must now handle non-JSON bytes and truncated/absent objects, not just valid-JSON-that-isn't-GeoJSON. Note ADR-035's ordering rule already creates a legitimate "row exists, object missing" state that must read as an **empty file**, so this path is exercised by correct operation, not only by corruption.
  - **New: content-type is now attacker-influenced.** The Storage API serves back the MIME type supplied at upload, so a replayed upload can claim `text/html`. Any public-serving path must **force** the content type and send `nosniff` rather than trust stored metadata. This is the sharing revisit-trigger above, arriving earlier than expected — via the storage layer rather than via a rendered viewer.

  The core finding stands unchanged and is *strengthened*: content validation was never the control, because arbitrary data wraps trivially inside a valid `FeatureCollection`. Nothing here argues for adding it.

## ADR-034 — Premium features gate scale, automation, and distribution, not capability

- **Status:** Accepted (2026-07-26). Extends [ADR-032](#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)'s "gate scale/persistence, not capability" from the *storage/file-count* levers to the *feature* axis; builds on the freemium framing ([ADR-019](#adr-019--the-cloud-epic-is-a-freemium-saas-free--local-paid--cloud)/[ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)); interacts with [ADR-033](#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos) (the sharing revisit-trigger) and [ADR-002](#adr-002--client-direct-access-with-rls-not-a-node-wrapper) (client-direct writes).
- **Context:** ADR-032 settled the *tier levers* (storage + file-count) but explicitly left "non-storage entitlements (e.g. premium tools)" as TBD — and the pricing analysis flagged that differentiating Pro on storage size alone is thin. The user proposed adding paid-plan features (share/collaborate, publish publicly, batch operations) and asked which could ride go-live cheaply vs. warrant their own phase. The tension to resolve: ADR-032 forbids gating *core capability* (editing/conversion is the acquisition funnel), so premium features must be defined so they don't reintroduce that gate.
- **Decision:**
  - **The premium axis is *scale, automation, distribution, and collaboration* — never core single-user capability.** The test for any paid feature: it gates *how much / how fast / with whom / how far it reaches*, not *whether the tool works*. The free editor stays fully capable; paid plans buy leverage on top of it. This is the rule future feature calls check against.
  - **Near-term slate (what's in, and where):**
    - **`save-as`** (clone the active file into a new named row) — a **core editor convenience, left ungated**; reuses the Phase 3 multi-file create path. **Phase 7d** (quick win; was 7c — Phase 7 renumbered 2026-07-27). *Automatic* version history is the future paid ("scale") counterpart — backlog.
    - **share-as-URL / publish read-only** — publish a file at an **unguessable token URL** with an unpublish/revoke action; ~~a small Node **public-read endpoint**~~ *(obsolete under ADR-035 — Supabase Storage serves the bytes directly; see the addendum below)* serves the file as **raw `application/json`** (safe headers: `nosniff`, non-HTML content-type, CORS-friendly) so the existing **import-from-URL** feature (and any other tool) can consume it. **Phase 7d** (quick win; was 7c). Serving *raw bytes* rather than rendering keeps ADR-033's sanitisation tail **off** (only a *rendered* public viewer would trip it). A public-read path does **not** violate ADR-002 — that guards the authenticated *write* path; serving a public file to a non-owner is a legitimately different concern.
    - **bulk operations** — a **premium** feature, shipping **bulk export first** as a finished thin slice, in **Phase 9's Premium-v1 slice** (paired with pricing finalisation). Bulk import and further bulk ops fill in **post-launch (Phase 10)**. Bulk operations gate *automation/scale* (doing an action many times at once), never the single-item action itself.
    - **hidden / comp / custom-paid plans** — the `plans` table gains a private **`description`** column and seeded hidden plans (`discount`, `god_mode`); **Phase 7a** (rides the `0005` re-apply). Comp/free plans are pure SQL (no Stripe); a hidden *paid* plan is a real Stripe price never listed in the upgrade UI (see `docs/RUNBOOK.md`).
  - **Collaborative editing is deferred** (email-invite ACL, "same-organisation"/teams, and real-time collab). The **publish-as-URL + import-from-URL pair is the v1 collaboration story** (owner publishes, recipient imports into their own copy) — no ACL, no RLS rewrite, no invite flow. Real-time collab is dropped outright.
  - **"Preview" / "early preview"** is the label for any future *see-new-features-first* perk (retiring "early access", which now names the `free` plan). It stays a soft marketing label — **nothing to build**. Priority support is **not** a paid feature (a solo maintainer can't promise an SLA — one honest support inbox for all, AI-assisted reply drafting).
- **Rationale:** Defining premium as scale/automation/distribution/collaboration keeps the funnel intact (ADR-032) while giving the paid tiers a real "why upgrade" story beyond raw storage. Sequencing by *architectural risk* — cheap, no-security-change items (save-as, publish-raw, hidden plans) ride the pre-beta phases; anything where "another human sees this file" (shared editing, a rendered public viewer) is a deliberate, tested phase — protects the beta timeline. "Partial at launch" is disciplined as *fewer features, each finished* (bulk **export** whole; bulk import later), never a half-working wide surface. The publish-raw framing is the key unlock: because import-from-URL wants raw geojson anyway, publish needs safe *serving* (headers), not the heavier output *sanitisation* ADR-033 reserved for rendered third-party consumption.
- **Alternatives rejected:**
  - **Gate core editing/conversion or export formats by tier:** rejected — that is the acquisition funnel (reaffirms ADR-032).
  - **Shared editing before go-live:** rejected for launch — dominated by three costs (an invite-by-email + pending-invite/claim-on-signup flow; rewriting the owner-only RLS boundary to consult a `file_shares` ACL; the whole-document-write clobber, which pulls in the parked per-feature model). Wants its own tested phase, if ever — publish+import covers the near-term need.
  - **Real-time collaboration:** rejected outright — fights the whole architecture (whole-doc writes, ADR-004 no-sync); a separate epic at best, and questionable fit for this product.
  - **Priority-support SLA / an in-app AI support bot as a launch perk:** rejected — an SLA a solo maintainer can't honour is worse than none; an AI support widget is its own mini-project (cost/abuse surface). Use AI to *draft* replies to a plain inbox instead.
- **Consequences:**
  - **[`03-rollout.md`](03-rollout.md):** Phase 7a gains the `plans.description` column + `discount`/`god_mode` seeds; Phase 7d *(was 7c)* gains save-as and share-as-URL (~~the latter adds the small public-read endpoint~~ — largely obsolete under ADR-035, see the addendum below); Phase 9 gains a **Premium-v1** slice (bulk export + pricing); a new **Phase 10 — post-launch premium iteration** holds the long tail.
  - **[`04-backlog.md`](04-backlog.md):** a premium-feature menu tagged by axis, plus the deferred long tail (bulk import, version history, publish discovery/directory + rendered viewer, shared editing).
  - **[`docs/RUNBOOK.md`](RUNBOOK.md):** documents adding hidden comp *and* paid plans.
  - **Revisit trigger stays ADR-033's:** the day publish grows a *rendered* viewer, or shared editing lands, output sanitisation becomes the control — designed into that feature, not retrofitted.
- **Addendum (2026-07-27) — publish gets cheaper under [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row); the small Node public-read endpoint is largely obsolete.** With the file living in Supabase Storage rather than a `jsonb` column, serving it publicly no longer needs an endpoint that reads a row and re-emits it — Storage serves the bytes directly, with the correct content type, from CDN. The **decision** (publish read-only at an unguessable URL, raw `application/json`, revocable, consumable by import-from-URL) is unchanged; only the mechanism gets simpler, and the Phase 7 quick win shrinks accordingly. Intended design, to verify before building: **one private bucket** plus an RLS policy granting `anon` read where the owning `user_files` row is published — a single copy, no expiry, publish/unpublish as a boolean flip. Two caveats ride with it: the cross-table subquery inside a `storage.objects` policy needs prototyping, and **CDN caching undermines revocation** (an unpublished file may keep serving until its TTL expires — for a revoke action that is a correctness bug, not a performance one). Fallbacks if either bites: signed URLs (expiring, which fights "published until revoked") or a separate public bucket (two copies, and a decision about whether the copy counts against quota). ADR-035 also adds a control this ADR did not anticipate: because upload-supplied MIME types are served back, the public path must **force** the content type + `nosniff` (see the ADR-033 addendum).

## ADR-035 — The GeoJSON blob moves to Supabase Storage; `user_files` becomes a metadata row

- **Status:** Accepted (2026-07-27). **Supersedes the inline-blob decision** of [ADR-001](#adr-001--backend-is-supabase) (which held Storage "in reserve for large files only" — the reserve is now called in) and [ADR-016](#adr-016--phase-2-schema-shape-refines-the-architecture-5-sketch)'s `geojson jsonb` column; **partly supersedes [ADR-022](#adr-022--monetisation-mechanics-user_plans-storage-quota-via-postgres-trigger-stripe)**, which asserted that moving to Storage would be "a cost lever, not a change to quota enforcement" — quota enforcement *does* change, and that is the bulk of this work. Promotes the "Large-file ceiling" item from [`04-backlog.md`](04-backlog.md). Preserves [ADR-002](#adr-002--client-direct-access-with-rls-not-a-node-wrapper) (client-direct, no Node hop on the blob path) and [ADR-004](#adr-004--two-isolated-storage-paths-no-sync) (the local path is untouched).
- **Context:** A **43 MB** GeoJSON file, imported by a logged-in user on staging, **took the whole Supabase project down** — twice, on two different projects, each requiring a manual restart. The trace is a `520` on the `PUT /rest/v1/user_files` (invalid origin response) immediately followed by a `521` on the subsequent `GET` (origin unreachable): PostgREST exhausts memory materialising the `jsonb` payload and the project stops serving. A 26 MB file works; the same 43 MB file is handled fine by the anonymous IndexedDB path, so this is a **cloud-path-only regression against the free product**.

  Four properties of the current design make this unfixable in place:
  1. **The blow-up is upstream of Postgres.** PostgREST dies parsing and binding the payload, so no `CHECK`, trigger, or RLS policy ever runs. There is **no server-side seam** in which to put a per-file size guard — the existing `enforce_storage_quota` trigger is downstream of the crash.
  2. **A client-side cap is UX, not a control.** [ADR-033](#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos) already establishes that a user can replay their own client-direct write with any body using their own valid token. So a client guard stops accidents, not the failure mode — and a single user, accidentally or not, can halt the service for **every** user. That is a self-inflicted denial-of-service surface on a shared instance.
  3. **Reads have the same ceiling as writes.** The `521` is the read-back. Even a row written by some other means could not be read out.
  4. **`jsonb` write amplification is per-edit.** A TOASTed value cannot be partially updated: every autosave re-compresses and re-writes the entire document as fresh TOAST chunks, writes comparable volume again to WAL, orphans the previous chunks for autovacuum, and ships it all to backups. Autosave has **no debounce** today (eleven call sites in `draw-manager.js`, each a whole-document write), so this is paid on every draw operation.

  Raising the instance's RAM was considered and rejected on its own terms: the memory cost is **per concurrent request**, so the real variable is *file size × concurrency*, not file size. It moves the cliff without removing it, and buys nothing against (3) or (4).
- **Decision:** **Move the GeoJSON bytes out of Postgres into Supabase Storage.** `public.user_files` keeps its identity, name, and timestamps and becomes a pure **metadata row**; the document itself becomes an **object** in a private bucket.
  - **Bucket:** `user-files`, **private**, with an explicitly-set `file_size_limit` and an allowed-MIME-type list. Created and configured **in the migration** (`insert into storage.buckets … on conflict do update`), not by hand in the dashboard, so it is versioned and reproducible per environment like every other schema object.
  - **Object path is `{user_id}/{file_id}.geojson`** — deterministic, derivable from the metadata row, and prefixed by the owner so RLS on `storage.objects` can key on the first path segment (`(storage.foldername(name))[1] = auth.uid()::text`). Owner-only `select/insert/update/delete` policies mirror the `user_files` policies exactly; `anon` gets nothing.
  - **Objects are stored as plain bytes, untransformed** — `application/json`, exactly what was uploaded.
  - **The object is authoritative; the row is descriptive.** There is no transaction spanning Postgres and Storage, so a total ordering is defined instead (see *Consequences*), chosen so that every partial failure degrades to *correct data with stale metadata*, never the reverse.
  - **The per-file size cap becomes the bucket's `file_size_limit`** — enforced by the Storage API at the edge, server-side, before the bytes are accepted. This is the guardrail [ADR-032](#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features) called for and that the current architecture had **nowhere to put**. **Set to `50000000` (decimal 50 MB), uniform across tiers and environments** (chosen 2026-07-27 — see the ADR-032 addendum), with the app's `MAX_FILE_SIZE_FOR_FILE_IMPORT` aligned to the same value so there is one ceiling, not two. Decimal rather than binary because Supabase's free plan caps uploads at 50 MB and a bucket limit must be ≤ the project's global limit. The *anonymous* path keeps this cap for editor-performance reasons only — IndexedDB itself handles 50 MB fine, which is precisely why the cloud path being the weaker one was intolerable.
  - **Quota enforcement splits across the two axes.** **File-count is unchanged** — `enforce_file_count` stays exactly where it is, on `user_files`, because the metadata row is still the thing being counted. **Storage bytes** must be re-based on `storage.objects.metadata->>'size'`, which is the only place that knows the real byte count. A client-written `size_bytes` column is explicitly **rejected as the source of truth** — it is spoofable by exactly the request-replay of ADR-033, and a quota whose input the client supplies is not a quota. The primary proposal is a `BEFORE INSERT OR UPDATE` trigger on `storage.objects` (the direct analogue of today's trigger), with a Node-issued **signed upload URL** gated on a server-side quota check as the documented fallback if triggering a Supabase-managed table proves unworkable. **Both are to be prototyped before the slice is committed to** — see *Consequences*.
  - **Cut over behind dead code, not a flag** (the user's call, 2026-07-27). The seam already exists, so the new backend is a third implementation behind `file-storage.js` and the cutover is a one-line change in the seam's routing. The Postgres blob path is left in the repo, unreachable, clearly commented as superseded, and deleted — along with the `user_files.geojson` column — once the Storage path is proven.
- **Rationale:**
  - **It is the only option that removes the failure mode rather than moving it.** Storage is an S3-backed object store: a PUT streams bytes and never materialises the document in a Postgres connection process, so a large file cannot exhaust the API tier. Everything else considered (bigger instance, client caps, chunking) leaves a single user able to degrade the service.
  - **It fixes the read ceiling too**, which no write-side mitigation does.
  - **It removes TOAST/WAL amplification entirely** — a PUT replaces the object: one write, no log-then-write, no dead tuples, no vacuum debt, no backup churn.
  - **It gives the per-file guardrail a real, server-side home** for the first time.
  - **The unit economics improve.** DB disk is the cost driver (the 2026-07 pricing analysis); object storage is materially cheaper per GB, and the workload's dominant direction — repeated whole-document autosaves — is **ingress**, which is the un-metered direction. Egress is not a new cost: reading a 43 MB `jsonb` row out of PostgREST already pays the same bytes; this only relabels the line item, and gains CDN cacheability on published files.
  - **Doing it now is far cheaper than doing it later.** There is **no production data** (ADR-014 — the prod project doesn't exist yet), so this is a code change plus a bucket, not a migration of real users' files. After beta it is a data migration with a correctness burden and a rollback plan. This is the last cheap moment.
  - **It costs no architectural principle.** Uploads stay client-direct with authorization by RLS — the boundary just moves from `user_files`' policies to `storage.objects`' policies (ADR-002 intact). The local path is untouched (ADR-004 intact). Tiers stay data rows (ADR-030 intact).
- **Alternatives rejected:**
  - **Scale the Supabase compute tier:** rejected — the cliff is a function of file size × *concurrency*, so it becomes unpredictable rather than absent; it is a permanent bill to keep doing the thing that doesn't work; and it addresses neither the read ceiling nor the write amplification.
  - **A client-side pre-flight size cap as the fix:** rejected **as the fix**, adopted as a *stopgap*. ADR-033's replay argument means it cannot be the control — but it converts today's crash into an honest error message for the 100% of users who aren't attacking anything, so it ships first, immediately, while the real work proceeds.
  - **Chunk the `jsonb` across multiple rows:** rejected — reassembly on every read, a new consistency problem, all of the TOAST/WAL cost retained, and the cure is strictly worse than the object store that already exists in the same product.
  - **Route large writes through the Node API:** rejected — reintroduces a server hop on the core write path (ADR-002), and relocates the memory blow-up from PostgREST to Node rather than removing it.
  - **`text` instead of `jsonb`:** rejected — avoids the parse cost but keeps every other property (TOAST, WAL, the PostgREST materialisation, the read ceiling), and loses the malformed-JSON rejection for no structural gain.
  - **One row per feature (`file_features`) — the delta model** ([`04-backlog.md`](04-backlog.md) *write granularity*): rejected **for this problem**, and kept distinct from it. It is the answer to *editing* cost, not to *blob* cost, and it is a data-model rewrite touching the draw manager, undo/redo, and every consumer. Blob externalisation and per-feature rows remain the two divergent large-file strategies; this ADR picks the first and leaves the second parked.
  - **Do nothing and cap the product at ~25 MB:** rejected — the anonymous free tier already handles 43 MB, so the cloud product would be *worse than the free one* at exactly the point a user is paying for it. The user called it "a deal breaker"; that is the correct read.
- **Consequences:**
  - **Failure ordering is now a design artefact, not an implementation detail.** Because no transaction spans the two stores:
    - **Save:** upload the object, *then* update the row. A failure between them leaves correct bytes with stale metadata, which self-heals on the next save.
    - **Create:** insert the row first (it allocates the `id` and is what `enforce_file_count` gates), *then* upload. "Row exists, object missing" must read as an **empty file**, so a failed upload degrades to a blank document rather than a broken one.
    - **Delete:** delete the object first, *then* the row. The reverse orphans an object that consumes quota and is invisible to its owner.
  - **Account deletion has a real gap that must be closed in the same slice.** `on delete cascade` from `auth.users` clears `user_files` and leaves **every object behind** — a database trigger cannot reach Storage. The existing `POST /api/v1/account/delete` (Phase 4, `service_role`) is the natural home: sweep the user's `{user_id}/` prefix *before* `admin.deleteUser`. A periodic reconciliation of objects with no owning row is the backstop. **This is a compliance obligation, not housekeeping** — "delete my account" must actually delete the files.
  - **Two migration-level reworks.** `public.user_storage_usage` (`0003`) must source `bytes` from `storage.objects` while keeping `file_count` from `user_files` (so a file with no object yet still counts). `enforce_storage_quota` (`0005`) is superseded by whichever mechanism the prototype selects; it stays in place, enforcing the old path, until the Postgres blob path is deleted.
  - **Storage RLS is a second security surface** and joins `user_files`/`user_settings`/`user_plans` in the two-account isolation test. It is the security-critical part of this slice, and the reason the slice is medium-risk rather than low.
  - **[ADR-033](#adr-033--no-server-side-geojson-content-validation-integrity-via-quota-and-tos)'s residual widens, and its third control becomes load-bearing.** `jsonb` at least rejected *malformed* JSON; an object store accepts **arbitrary bytes**. The two intent/cost controls (quota, ToS acceptable-use) are content-agnostic and unaffected, but **reader robustness** — graceful read-back of non-GeoJSON, already a Phase 7 task — moves from prudent to required. ADR-033's core finding is unchanged: content validation was never the control, because arbitrary data wraps trivially inside a valid `FeatureCollection`.
  - **A new content-type concern for publish.** The Storage API serves back the content type supplied at upload; a replayed upload could set `text/html`. Any public-serving path must **force** the content type and send `nosniff` rather than trusting stored metadata — otherwise a published file is stored XSS on the `*.supabase.co` origin. This is precisely the revisit-trigger ADR-033 anticipated, arriving earlier than expected.
  - **Publish gets simpler and [ADR-034](#adr-034--premium-features-gate-scale-automation-and-distribution-not-capability)'s design changes.** The planned small **Node public-read endpoint** is largely obsolete: Supabase can serve the bytes directly, with the right content type, from CDN. Intended design for Phase 7 (verify before building): a **single private bucket** plus an RLS policy granting `anon` read where the corresponding `user_files` row is published — one copy, no expiry, and publish/unpublish is flipping a boolean. Two caveats attached: the cross-table subquery in a `storage.objects` policy needs prototyping, and **CDN caching undermines revocation** (an unpublished file may keep serving until its TTL expires), which for a revoke action is a correctness problem, not a performance one. Signed URLs (expiring — fights "published until revoked") and a separate public bucket (two copies) are the fallbacks.
  - **CDN caching must be decided deliberately on the authenticated path too.** A just-saved file served stale from cache reads to the user as "my edit disappeared." Short/no cache for owner reads, long cache only for published files.
  - **Export improves, and a backlog item gets cheaper.** The bundle can no longer be one `select`; it becomes N object downloads — which is exactly the shape of the backlogged **export-as-zip of individual `.geojson` files**, now the natural implementation rather than extra work.
  - **Byte-exact round-tripping becomes possible where it matters.** `jsonb` normalises — it reorders keys, drops duplicates, strips whitespace — so the cloud path today does *not* return a user's file as they gave it. Objects do. The practical gain is bounded (the app re-serialises from the draw manager on save, so exactness survives only import → export without editing), but the store no longer destroys it.
  - **What this does *not* fix: editing cost.** Whole-document writes on every draw operation remain wasteful, and on a phone or a weak connection re-uploading 20 MB every few seconds is a real user harm independent of billing. **Debounced/coalesced autosave is required alongside this work**, not after it. Per-feature deltas stay backlogged.
  - **Two prototypes gate the slice**, because both are load-bearing and neither should be assumed: (1) a trigger on `storage.objects` fires and rejects cleanly without leaving orphaned bytes, and (2) a `storage.objects` RLS policy may contain a cross-table subquery. If (1) fails, the fallback is Node-issued signed upload URLs; if (2) fails, publish falls back to a separate public bucket.
  - **Docs affected:** [`01-architecture.md`](01-architecture.md) §2 + §5 (the blob is no longer inline), [`03-rollout.md`](03-rollout.md) (Phase 7 re-sliced; the publish quick win re-scoped), [`04-backlog.md`](04-backlog.md) (large-file ceiling promoted; write-granularity note updated), [`RUNBOOK.md`](RUNBOOK.md) (bucket config + the orphan sweep).

## ADR-036 — Local storage buffers cloud writes: the recovery journal is promoted; IndexedDB as a staging area is rejected

- **Status:** Accepted (2026-07-28). **Amends [ADR-025](#adr-025--connection-loss-resilience-for-cloud-edits-level-1-retry--reconnect-flush--save-status)**, whose Level 2 journal was backlogged behind "build only if users actually report lost work" — that trigger is retired and the journal is **scheduled for slice 7c**, after [ADR-035](#adr-035--the-geojson-blob-moves-to-supabase-storage-user_files-becomes-a-metadata-row)'s 7b-2. Preserves [ADR-004](#adr-004--two-isolated-storage-paths-no-sync) by keeping the carve-out ADR-025 already defined: one-way, self-clearing, never a sync path. Records the **rejection of a larger alternative** (IndexedDB as the source of truth for cloud users) raised 2026-07-28.
- **Context:** Phase 7b-1 added coalesced autosave, and tuning it went three rounds against real testing. Each round exposed the same structural fact: **durability was coupled to upload frequency.** The debounce window existed to save the user's bandwidth, but every millisecond of it was also a millisecond of edits a refresh could destroy — the two goals were being traded against each other with a single number.

  Three findings from that work are load-bearing here:
  1. **The `pagehide`/`visibilitychange` flush does not work.** The browser abandons the write during teardown, and it is several async hops deep before a byte lands. It loses reliably, not occasionally. It must never again be cited as the reason a window is safe to widen.
  2. **`beforeunload` warns; it does not write.** It was pulled forward from 7c and does help — mostly because its dialog is synchronous and buys the in-flight write the time the user spends reading it — but it cannot complete an upload the user declines to wait for.
  3. **No flush mechanism survives page death at our payload sizes.** `fetch(keepalive)` caps at 64 KB; `sendBeacon` cannot set the auth headers Supabase requires.

  The window is now priced by measured save cost, which resolved the acute bug, but the coupling remains. A local buffer removes it: if an edit is durable the instant it happens, upload timing becomes a pure bandwidth question with no data at stake.
- **Decision:** **Local storage buffers cloud writes as a journal. The cloud remains the single source of truth.**
  - **Scope: the active document only.** The app edits one document at a time, so the journal holds the un-acknowledged state of that document and nothing else. It is *not* a local mirror of the user's library.
  - **Keyed by `file_id`.** Even with one active document, cloud users switch files ([ADR-018](#adr-018--phase-3-multi-file-model-and-file-lifecycle)), and an unkeyed journal would restore file A's contents into file B — the same class of bug as the 7b-1 flush boundaries. One column, but not optional.
  - **The journal write is IMMEDIATE, on every edit.** This is a constraint, not a preference: a journal on a debounce inherits the exact teardown problem it exists to solve, because it is still an async IndexedDB write. Affordable precisely because it is local.
  - **The upload is scheduled separately and lazily.** Two timers with unrelated jobs — durability and bandwidth — rather than one number trying to serve both.
  - **Recovery is offered, never applied silently.** On load, an un-acknowledged journal entry for the active file raises *"You have unsaved changes from your last session — restore or discard?"* The user decides. Silent application would be a sync decision made on the user's behalf, which is exactly what ADR-004 forbids.
  - **Cleared on acknowledgement, and on sign-out.** Clearing on sign-out is a **privacy requirement**, not tidiness: on a shared browser, cloud bytes must not outlive the session.
  - **Sequenced after 7b-2**, deliberately — see *Consequences*.
- **Rationale:**
  - **It decouples durability from upload frequency**, which is the whole point. The adaptive-window machinery built in 7b-1 (`lastSaveDurationMs`, the cheap/costly split, the leading-edge write) exists only to manage a trade that then stops existing.
  - **It closes the offline gap honestly.** Edits are safe locally, the indicator says "not synced", and they upload on reconnect — instead of today's failing saves.
  - **It demotes `beforeunload` from load-bearing to belt-and-braces**, which is where a mechanism that depends on the user reading a dialog belongs.
  - **It needs no conflict resolution**, because the journal is never authoritative and recovery is a user choice, not a merge.
- **Alternatives rejected:**
  - **IndexedDB as a staging area — the local store becomes the source of truth for cloud users, with a scheduler syncing to Supabase.** Proposed 2026-07-28 on the grounds that it would unify the two paths' code, deliver offline support, and possibly retire the seam. Rejected — it is **replication**, and the details it defers are the system:
    - **It requires conflict resolution.** The moment a local copy can diverge, two devices editing the same file produce two whole-document versions with no merge available — only a winner and a silently destroyed loser. This is the "no sync" non-goal of ADR-004, which exists to avoid exactly this.
    - **The Pro tier refutes it directly.** Pro is 20 GiB; browser quota cannot mirror that, so the local store needs eviction — and **the moment eviction exists, the cloud is authoritative again.** What is left is a cache plus a seam, i.e. the current architecture with more parts.
    - **It relocates quota rejection to the worst possible moment.** Today an over-limit write is refused synchronously and `PlanLimitDialog` is tied to the action that caused it ([ADR-032](#adr-032--plan-tiers-differentiated-by-storage-and-file-count-not-features)). Under staging the user edits for twenty minutes and is then told none of it can be uploaded.
    - **It creates a privacy exposure that is currently structural.** Cloud data would live in the browser store and must be purged on sign-out; today that is impossible by construction.
    - **It does not fix the crash.** 43 MB still eventually reaches PostgREST. ADR-035 is required either way.
    - **The simplification claim inverts.** The seam is ~50 lines of routing and is what makes the ADR-035 cutover a one-line change; the replacement is a per-file sync state machine, a scheduler with backoff, a **multi-file local schema** (the local path stores one document under one key — so "the same code as the browser path" is false before you start), deletion/rename propagation, conflict UX, and eviction policy.
    - **"This is how mobile apps work" is true but does not transfer.** Those apps sync **records** via frameworks nobody hand-rolls (Core Data/CloudKit, Room/Firestore, Realm, PowerSync, ElectricSQL, Yjs) — small rows where last-write-wins is survivable. Local-first over multi-megabyte blobs is the combination those frameworks specifically avoid. **The genuine prerequisite is the per-feature row model** (`file_features`, [`04-backlog.md`](04-backlog.md) *write granularity*): with one blob "what changed?" is unanswerable, so sync can only pick a winner; with one row per feature a change is a small independent fact and two devices editing different features can both be honoured. That model stays parked, and true local-first is not reconsidered before it lands — and then with a library, not by hand.
  - **A dedicated sync/offline package for the journal itself:** rejected as over-engineering. **Dexie is already a dependency** and the journal is a table with three operations. `idb` / `idb-keyval` are likewise unnecessary.
  - **Widening the debounce and relying on `beforeunload`:** rejected — this is what 7b-1 did, and it is what testing rejected. See *Context*.
- **Consequences:**
  - **Sequenced after 7b-2, and this is the deciding reason:** the journal's retry logic must classify **which failures are worth retrying**, and 7b-2 changes that answer completely — different status codes, a bucket-level size rejection at the edge, and the row-then-object ordering whose partial failure states ADR-035 defines. Building it first means writing failure handling against a backend about to be deleted. Supporting reasons: the acute data-loss bug is already closed, and 7b-2 remains the highest-severity open defect.
  - **It deletes the 7b-1 adaptive window.** `lastSaveDurationMs`, `lastSaveIsCheap()`, the cheap/costly constants and the leading-edge branch all become unnecessary once durability is local. Expect a **net increase in total code** even so — recovery prompt, clear-on-ack, clear-on-sign-out, the file-id association, a staleness check, an "unsynced" status state, plus ADR-025 Level 1's retry/backoff. The gain is in the **shape**: explicit durable buffer with explicit recovery, replacing timing heuristics that trade data loss against bandwidth. *"How short must the window be before we lose data?"* stops being a question anyone has to answer.
  - **Large documents still cost something locally.** Writing 40 MB to IndexedDB on every edit is the main-thread cost the local debounce was addressing, so the journal timer is short rather than zero for costly documents. Cheaper than an upload, but not free.
  - **A future option worth remembering: `workbox-background-sync`.** A Service Worker queue is the only mechanism that can finish an upload *after the tab closes*, which would retire `beforeunload` entirely. The app has no Service Worker today; revisit in 7d or later, not with this work.
  - **ADR-004's carve-out is now exercised, not hypothetical.** It stays narrow by construction: one document, un-acknowledged writes only, user-confirmed recovery, cleared on sign-out. Any proposal that widens it into a mirror is this ADR's rejected alternative and should be read as such.
  - **Docs affected:** [`03-rollout.md`](03-rollout.md) (7c gains the journal), [`04-backlog.md`](04-backlog.md) (the Level 2 item is promoted and its "only if users report lost work" trigger retired).
